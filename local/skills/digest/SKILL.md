# Digest

## 목적

공식문서를 읽어 배우고, 그 주제의 [`knowledge/`](../../contexts/directory-roles.md)를 이번 출처 기준으로 다시 쓴다.

읽고 이해한 것은 대화가 닫히면 사라진다. 배우는 일과 남기는 일을 한 세션 안에 묶어야 그 주제의 지식이 실제로 갱신된다.

## 이번에 읽는 문서가 기준이다

digest는 지식을 **쌓기만 하는** 도구가 아니라 **다시 쓰는** 도구다. 이번에 읽는 문서가 그 주제의 현재 내용이고, KA에 이미 있는 것은 예전에 정리해둔 것이다.

처음 배우는 주제면 겹칠 게 없으니 이 원칙이 쓰일 일도 없다. 쓰이는 건 **기존 내용과 부딪힐 때**이고, 그때는 이번에 읽는 문서가 이긴다.

- 기존 파일명·폴더 구조는 참고일 뿐 지켜야 할 틀이 아니다. 이번 문서의 짜임새가 더 맞으면 기존 배치를 갈아엎는다.
- 기존 Q&A는 지워도 된다. 낡은 지식은 없느니만 못하다 — `/review`·`/exam`이 옛 답을 정답으로 채점하기 때문이다.
- 단, 지우고 다시 쓰는 건 **ON에서 알린 겹침 목록 안에서만** 한다 (「ON — 모드 시작」의 겹치는 것 찾아 알리기).

이 원칙이 쓰이는 흔한 상황: 예전에 드문드문 읽은 페이지를 처음부터 다시 읽을 때, 문서가 버전업돼서 내용이 달라졌을 때, 백로그에 적어둔 주제를 새 문서로 정리하며 없앨 때.

## 공통 규칙

모든 모드에서 Q&A를 저장할 때 적용되는 규칙이다.

### 내용 분류
- 영어 원문이 있으면 그대로 보존하여 Official Answer로 사용
- **원문 합성 금지**: 여러 출처의 문장을 단어 단위로 짜깁기하여 새로운 문장을 만들지 않는다. 단, 서로 다른 출처의 원문 문장을 그대로 이어 붙이는 것은 허용한다.
- **사용자가 직접 작성한 한글 메모**는 User Answer로 분류
- **영어 원문 없이 한글만 제공된 경우**: User Answer로 작성한다 (AI의 OA 신규 생성 금지 — [content-format.md](../../contexts/content-format.md) 참고).

### 해설은 knowledge에 저장하지 않고, explained로 보낸다

대화형 모드의 line-by-line 해설을 **knowledge/ 파일에 저장하지 않는다** — 비유·통찰 등 보조 내용은 explained/에 담당하며 knowledge/에 중복 보관하지 않는다.

대신 **OFF 2단계에서 확정된 질문 전체를 `explained/<rel>.md`로 저장**한다. **explained 공통 양식**(`# <질문>` H1 + `## 도입` / `## 본문` / `## 종합`, H2 사이 `---`)을 쓰고, 세션 중 사용자가 헷갈려서 풀어준 **오해·재설명도 본문에 녹여 포함**한다 (별도 `## 오해 교정` 섹션을 만들지 않고 본문에 녹인다). 이로써 digest 세션에서만 드러난 사용자 오해가 휘발되지 않고 학습 캐시로 남는다.

소유권: 해당 질문 섹션이 `explained/<rel>.md`에 **이미 있으면 덮어쓰지 않는다** (먼저 만든 쪽 보존). 저장 위치·섹션 순서·소유권 규칙은 [explanation-guide.md](../../contexts/explanation-guide.md) §6 참고.

**예외 — 이번 세션에 그 질문의 knowledge를 갈아끼웠으면 explained도 다시 쓴다.** OFF 1단계에서 그 질문을 다시 쓰거나 갈아끼우거나 보충했다면 기존 explained 섹션을 남기지 않고 덮어쓴다. 안 그러면 새 내용 옆에 옛 해설이 남아, knowledge는 v16인데 설명은 v14인 상태가 된다. "먼저 만든 쪽 보존"은 **손대지 않은 질문**에만 적용된다.

### Frontmatter publishable

- **새로 만드는 knowledge/ 파일의 frontmatter에 `publishable: true`를 자동으로 박는다.** digest는 공식문서 1차 소스를 기반으로 하므로 외부 노출 가치가 검증된 입력이다.
- 기존 파일에 추가할 때는 frontmatter를 건드리지 않는다 (이미 있는 값 유지).
- 사용자가 명시적으로 false를 원하면 그 결정을 따른다.

### 이미지 alt text 필터링
사용자가 붙여넣은 텍스트에는 이미지의 alt text가 섞여 들어올 수 있다. 주어-서술어 구조가 없는 나열형 문장, 이미지 캡션으로 추정되는 문장은 Official Answer에서 제외한다. 해설 시에도 본문과 구분하여 취급한다.

### 이미지 다이어그램 처리
사용자가 공식문서의 다이어그램/구조도 이미지 URL을 함께 제공하면, 이미지를 로컬에 저장하지 않고 아래 방식으로 처리한다:
1. WebFetch로 이미지 내용을 파악한다
2. 이미지의 구조를 **텍스트 다이어그램**(ASCII art, 코드블록)으로 변환하여 OFF 2단계에서 생성하는 explained/ 섹션에 삽입한다
3. 원본 이미지 URL은 explained/ 섹션 하단에 `원본 다이어그램: [URL]` 형태로 기록한다

이렇게 하면 복습 시 이미지를 매번 fetch하지 않고 텍스트로 바로 설명할 수 있다.

### 범위 제한
사용자가 제공한 내용의 범위 내에서만 Q&A를 작성한다. 출처 URL을 방문하여 사용자가 언급하지 않은 추가 내용을 가져오지 않는다.

### User/Additional Answer → OA 교체
새 영어 원문이 들어왔을 때, 기존 knowledge/ 문서에서 Official Answer 없이 User Answer 또는 Additional Answer만 있는 질문과 매칭되면 OA로 교체한다.

- 기존 User Answer / Additional Answer는 삭제한다
- 새 영어 원문을 Official Answer로 저장한다
- 교체 전 사용자에게 확인받는다: "X 질문의 User Answer를 OA로 교체할까요?"

### 기존 미완성 질문 매칭

Q&A를 새로 만들기 전에, 기존 knowledge/ 문서에서 미완성 질문을 2단계로 검색한다. 마커 정의는 [document-structure.md](../../contexts/document-structure.md)의 "미완성 질문 처리" 참고.

**통째로 다시 쓰기로 한 파일에는 적용하지 않는다** — 그 파일의 빈칸을 채우는 게 아니라 파일 자체를 새로 쓰기 때문이다.

**1단계: `[UNVERIFIED]` 질문 검색**
- 사용자 내용과 관련된 마커 질문이 있는지 검색한다
- **매칭됨**: 새 내용으로 답변을 어떻게 채울지 사용자에게 확인 후 처리한다.
  - 공식 출처 원문이 들어왔다 → Official Answer를 채우고 마커 제거 (Questions 목록·본문 헤딩 양쪽). 기존 Additional Answer가 있으면 삭제한다.
  - AI 추정 답변만 가능하다 → Additional Answer를 채우고 마커를 `[UNVERIFIED]`로 변경 (이미 `[UNVERIFIED]`이면 답변 보강만)

**2단계: 답변 본문 내 `TODO` 문자열 검색**
- 1단계 이후, 답변 본문에 `TODO` 문자열이 포함된 항목을 추가로 검색한다
- **매칭됨**: 해당 `TODO` 부분만 교체/보충한다. 질문이나 전체 답변을 교체하지 않는다

**매칭 안 됨**: 새 Q&A를 작성한다. 마커는 아래 "마커 결정" 규칙으로 정한다.

답변을 채울 때, 해당 질문에 대한 **직접적인 답**이 되는 내용을 작성한다. 같은 파일 내 다른 답변의 문장을 그대로 복사하지 않는다.

### 마커 결정

새 Q&A를 만들 때 답변 상태에 따라 마커를 결정한다. 마커 사용 조건과 정의는 [document-structure.md](../../contexts/document-structure.md)의 "미완성 질문 처리" 참고.

| 상태 | 마커 |
|---|---|
| 공식 출처 원문 또는 후보 Reference 확보 | 없음 |
| 출처 단서 없음 | `[UNVERIFIED]` |

답변 섹션은 비어 있어도, User/Additional Answer가 채워져 있어도 무관하다 (마커는 OA/Reference 부재 상태만을 의미).

### Official Answer 길이 관리

OA는 단락 여러 개로 구성될 수 있다 ([content-format.md](../../contexts/content-format.md)의 "OA 단락 통합"). 길이 룰은 아래 단위별로 적용한다:

- **단락 단위**: 한 단락이 6문장을 초과하면 문장 정리 또는 단락 분리를 검토한다.
- **전체 단위**: OA 전체가 15문장을 초과하면 질문 분리를 검토한다.
- 테이블·코드블록·리스트는 문장 수에서 제외한다.
- 최종 판단은 사용자가 한다.

## 대화형 학습 (ON/OFF)

세션은 **URL 하나당 하나**다. 흐름은 두 국면으로 나뉜다.

```
ON [URL]                 페이지 요약. 겹치는 기존 문서가 있으면 목록으로 알린다 (묻지 않는다).
  ↓
루프 — 페이지 순회      문장마다 [인용 → 해설]을 브라우저 페이지로 띄우고, 사용자가 문장마다 저장·해설·버림을 고른다. 질문 제안 없음.
  ↓  (페이지를 끝까지 다 볼 때까지 붙여넣기 반복)
OFF 1단계 — 질문 확정·저장   겹친 파일을 어떻게 할지 정하고, 저장 판정된 재료로 질문을 뽑아 knowledge/에 저장
  ↓  (사용자 승인·저장 완료 후 이어서)
OFF 2단계 — 산출물 생성     explained 생성 → 표현 다듬기 → 소스 충실도 검증
```

질문 제안을 순회 중이 아니라 순회 후로 미루는 이유는 둘이다. 페이지 뒷부분이 앞부분 질문의 답을 완성하는 경우를 놓치지 않기 위해서, 그리고 결국 버려질 문장에 제안 비용(중복 grep·보충 검토·위계 배치)을 쓰지 않기 위해서다.

### ON — 모드 시작

[production-guide.md](../../contexts/production-guide.md)의 **Before** 실행.

출처 URL을 기록하고, WebFetch로 해당 페이지의 텍스트 콘텐츠를 가져와 **원본 참조 텍스트**로 보관한다. 이후 단락 검증에 사용한다.

**출처 URL 한글 요약**: 첫 응답에서, 보관한 원본 참조 텍스트를 근거로 페이지 전체의 **한글 요약을 먼저 출력**한다 (추가 fetch 불필요 — 위에서 가져온 텍스트를 재사용한다). 사용자가 세션 진입 즉시 무엇을 학습할지 조망하는 용도다. 요약에는 내용 개요에 더해 아래 축들의 구분을 포함한다:

- **실질적 쓰임새 차이**: 이 페이지를 알면 개발자의 코드 작성 방식이 직접적으로 달라지는 내용 (예: Fixtures — beforeEach 대비 작성 규칙 자체가 달라져 반드시 인지해야 하는 실전 가이드)
- **몰라도 지장 없는 내부 원리**: 알면 유익하지만 코드 작성법 차이를 직접 유발하지 않는 내부 동작·인프라 수준의 내용

요약이 아래 고정 안내보다 **반드시 먼저** 나간다. 순서: (1) 한글 요약 → (2) 겹치는 것 찾아 알리기 → (3) 고정 안내 블록.

**겹치는 것 찾아 알리기**: 이 주제로 KA에 이미 있는 것을 찾아 요약 뒤에 목록으로 보여준다. 요약 뒤에 오는 이유는, 무슨 내용을 배울지 봐야 어느 기존 문서가 갈릴지 판단할 수 있어서다. 아래 셋을 다 훑어 겹치는 것을 모은다.

- **URL**: 출처 URL이 기존 knowledge/ 문서의 Reference에 이미 있는지
- **주제**: 페이지가 다루는 개념·태그·폴더로 knowledge/를 grep — **URL이 안 걸려도 반드시 한다.** 같은 내용이 다른 출처로 이미 들어와 있을 수 있다 (「중복 검사」에 적힌 것과 같은 함정)
- **백로그**: 그 주제로 적어둔 백로그 항목 (세션 시작 때 뜨는 목록에서 고른다)

**손댈 범위는 언제나 겹치는 것 전체다 — 묻지 않는다.** 매번 같은 답("전체")이 나오는 것을 매 세션 확인받는 건 순수한 마찰이다. 목록은 "무엇이 갈릴 수 있는지" 알리는 통보이지 승인 요청이 아니므로, "범위를 정해주세요"라고 묻지 말고 곧장 고정 안내로 넘어간다. 사용자가 특정 파일을 빼라고 말하면 그때 그 파일만 뺀다.

- ❌ (사례) `reacting-to-input-with-state` 세션에서 겹치는 파일 둘을 나열한 뒤 "범위를 정해주세요, 안 정하시면 추가·보충만 합니다"로 물음 → 사용자: "지우고 다시 써도 되는 범위는 전체가 맞아. 이거 물어보라고한거야? 언제나 인데."
- ✅ 교정: 목록만 보여주고 "이 파일들이 이번 문서 기준으로 갈릴 수 있습니다"로 끝낸 뒤 바로 고정 안내를 낸다.

겹치는 게 없으면 조용히 넘어가 고정 안내로 진행한다.

여기서 하는 건 **알림뿐이고, 파일을 지우지는 않는다.** 파일마다 어떻게 할지(통째로 다시 쓰기 / 일부만 갈아끼우기 / 그대로 두기)는 페이지를 다 읽은 뒤 OFF 1단계에서 정한다. 아직 안 읽은 뒷부분이 기존 문서 내용을 근거로 쓸 수 있기 때문이다.

겹침을 OFF가 아니라 여기서 찾아두는 이유는 **루프의 저장 판정이 여기 매달려 있어서**다. 갈아엎을 파일 안에서는 "기존에 이미 있음"의 뜻이 뒤집히는데, 이 판정은 문장마다 찍히므로 늦게 찾으면 페이지 내내 낡은 기준으로 「버림」이 쌓인다.

**폴백 — URL과 단락이 함께 온 경우**: 사용자는 원칙적으로 `ON [URL]`만 먼저 주고 요약·안내를 본 뒤 단락을 붙여넣지만, URL과 영어 단락이 한꺼번에 온 경우에도 요약을 건너뛰지 않는다 — 요약을 먼저 출력한 뒤 그 단락을 「루프 — 페이지 순회」로 넘긴다.

이어서 아래 안내를 출력한다:

```
digest 모드 시작.
단락을 붙여넣으면 문장마다 해설한 화면을 브라우저로 띄웁니다.
거기서 문장마다 저장·해설·버림을 고르고 제출·복사한 뒤 복사된 JSON을 그대로 붙여넣어 주세요.
페이지를 끝까지 본 뒤 OFF 하면, 저장으로 고른 내용만 모아 질문을 뽑습니다.
단락을 붙여넣어 주세요.
```

### 루프 — 페이지 순회

사용자가 단락을 붙여넣을 때마다 아래를 수행한다. **이 단계에서는 질문을 제안하지 않고, 파일에 저장하지도 않는다.**

#### 0. 원본 페이지 검증

붙여넣은 단락의 핵심 문장이 원본 참조 텍스트에 포함되어 있는지 확인한다.

- **포함됨**: 다음 단계로 진행
- **포함되지 않음**: 해설을 진행하지 않고 아래 안내를 출력한다:

```
이 단락은 현재 URL 페이지에 없는 내용입니다.
다른 페이지의 단락을 붙여넣으셨나요?
새 URL을 알려주시면 해당 페이지로 전환합니다.
```

사용자가 새 URL을 제공하면 WebFetch로 다시 가져와 원본 참조 텍스트를 교체하고, 해당 단락의 해설을 이어서 진행한다.

#### 1. 문장마다 [인용 → 해설] — 브라우저 페이지로 낸다

해설은 **채팅이 아니라 브라우저 페이지**에 담는다. 사용자가 저장할 문장을 고르려면 채팅에서 문장을 손으로 복사해 되붙여야 했고, 그 과정에서 문장이 섞여 어느 것을 지정했는지 되짚는 일이 실제로 생겼다. 화면에서 문장마다 고르게 하면 그 왕복이 사라진다.

붙여넣은 단락의 **모든 문장·코드블록**을 문장 하나당 카드 한 장으로 만든다. 카드 한 장의 구성은 지금까지 채팅에 쓰던 것과 같고, 담기는 자리만 바뀐다.

1. **원문 인용** — verbatim으로 그대로 옮긴다. 이 인용이 OFF 1단계에서 Official Answer의 원본이 되므로 손대지 않는다.
2. **한글 의역** — 원문 의미를 한국어로 푼다. 사용자가 영어→한국어 변환 부담을 지지 않게 하는 줄이다. **판정은 라디오가 지고, 이 칸은 어디까지나 의역이다** — 판정 사유로 바꿔치기하지 않는다 (§2).
3. **영단어 해설** — 그 안의 중요 영단어를 `단어: 이 문장에서의 의미` 형식으로 짚는다. 짚을 단어가 없으면 생략한다.
4. **라디오 3택** — 저장 / 해설 / 버림. 기본 선택은 AI 판정으로 미리 찍어둔다 (§2).

2·3은 [CRITICAL] `local/contexts/explanation-guide.md` §1 「본문」의 기존 양식 그대로다 — 카드를 쓰기 전에 그 파일을 연다. 여기 옮겨 적힌 것은 카드 구성뿐이고 양식·금지는 그쪽이 정본이라, 기억으로 쓰면 옮겨 적히지 않은 항목을 통째로 어긴다. **라디오를 옆에 두는 것이지 기존 해설을 대체하는 게 아니다** — 의역이나 영단어 해설을 빼고 라디오만 내보내지 않는다. 긴 문장은 §1의 「끊는 기준」대로 콤마·접속사 단위로 쪼개 조각마다 의역·단어 해설을 달되, 카드는 문장 하나에 하나이므로 라디오도 하나만 둔다. 코드블록·삽화 캡션은 영단어 해설 없이 [인용 → 한 줄 설명 + 라디오]로 처리한다.

무엇이 학습가치가 있고 없는지를 AI가 미리 정해 **해설을 건너뛰지 않는다.** 해설에는 **스킵("넘어간 것") 경로가 없다** — 거르는 일은 라디오가 하고, 해설은 전부 한다.

**깊이는 학습가치에 비례해 조절**한다 (빼는 게 아니라 길이를 줄인다):

- 개념·정의·실무 함의가 있는 문장 → 인용 + 충실한 해설 + 필요한 용어 풀이
- 수사적 도입·전환·군더더기 문장(비유, "다음 섹션 예고" 등) → 건너뛰지 말고 **인용 + 한 줄 의역**으로 처리한다. 여기서도 의역이 먼저다 — 역할을 짚고 싶으면 의역 뒤에 한 마디 붙인다 (`하지만 여기에는 또 하나 작용하는 요인이 있다. (다음 논지를 끌어오는 전환 문장)`). 역할 라벨만 적고 의역을 생략하는 것이 §2의 [CRITICAL] 사고 그 자체다.

즉 깊이는 문장마다 달라도, **어떤 문장도 해설 없이 넘어가지 않는다.**

##### 페이지 만들기·열기

카드 내용을 스펙 JSON으로 적어 아래로 넘긴다. 페이지 골격·판정 뱃지·제출 payload는 렌더러가 짜고, 저장 경로·인코딩·오픈 방식은 그다음 스크립트가 정한다. 열린 절대경로가 돌아오면 채팅에 그대로 적는다.

**스펙 JSON은 레포 안에 만들지 않고 `os.tmpdir()` 아래에 쓴다.** 아래를 한 번에 실행한다 — 스펙을 Write 도구로 따로 만들지 말고 heredoc으로 그 자리에서 넘긴다.

```bash
SPEC="$(node -p 'require("os").tmpdir()')/ka-digest-<slug>-<회차>.json"
cat > "$SPEC" <<'SPEC_JSON'
{ ...스펙... }
SPEC_JSON
npm run --silent build-page -- digest-cards < "$SPEC" \
  | node {{contexts}}/local-html-roundtrip.mjs open ka-digest - --slug <slug>-<회차>
```

- 쓸 자리를 따로 찾지 않는다. 위 `node -p`가 그 자리를 주므로 `mkdir`·`ls`·`find`·`echo %TEMP%`를 돌릴 일이 없다.
- 중간 파일이 레포 안(특히 `.claude/` 하위)에 떨어지면 새 파일로 자동 staged되고, 지우려면 승인 프롬프트가 뜬다. 임시 폴더에 쓰면 둘 다 안 걸리므로 뒤처리도 하지 않는다 — 최종 HTML도 같은 곳에 떨어진다.

스펙은 `{ slug, round, summary, cards: [{ src, ko, words: [{ word, meaning }], verdict }] }`이고, 필드가 위 네 칸과 1:1이다 (`verdict`는 라디오에 미리 찍어둘 AI 판정 — `save`·`explain`·`drop`).

- `<slug>`는 출처 URL의 마지막 경로 조각을 소문자·하이픈으로 바꾼 값 (예: `headings-and-paragraphs`). `<회차>`는 이 세션의 붙여넣기 순번(1부터).
- **`src`에는 원문만 담는다.** 이 인용은 OFF 1단계에서 Official Answer의 원본으로 그대로 옮겨지므로 렌더러가 통째로 이스케이프한다 — 태그를 적어도 글자로 보인다. 굵게·코드 표시가 필요하면 `ko`·`words`에서 한다(그쪽은 마크업이 그대로 나간다).
- 페이지는 붙여넣기 1회당 새로 만든다. 이전 회차 페이지는 건드리지 않는다.

##### 채팅에 쓰는 것

원문·의역·영단어 해설·단락 요약을 채팅에 **쓰지 않는다.** 채팅에 남기는 것은 아래 세 줄뿐이다.

```
{N}문장으로 {회차}회차 페이지를 열었습니다.
C:\Users\...\Temp\ka-digest-{slug}-{회차}.html
문장마다 고른 뒤 제출·클립보드 복사를 누르고 복사된 JSON을 그대로 붙여넣어 주세요.
```

#### 1-0. 누락 방지 — 전 문장 카드 검증

붙여넣은 단락의 **모든 문장·코드블록**이 페이지에 카드로 들어갔는지 확인한다. 계정(account) 경로는 하나뿐이다:

- **카드 있음** — 원문 인용 + 최소 한 줄 의역 + 라디오 3택 (군더더기 문장도 "한 줄 역할 짚기"로 카드에 포함)

카드 없이 *말없이* 빠진 문장이 **0개**여야 한다. 스킵("넘어간 것") 경로를 없앴으므로 문장을 빼는 선택지 자체가 없다 — 모든 문장은 카드가 되고, 모든 카드에 라디오가 붙는다.

**압축 인용 금지**: 여러 문장을 한 카드에 `...`로 뭉개고 그중 일부만 해설하지 않는다. `...`에 묻힌 문장은 말없이 사라진 것과 같다. 문장을 살려 인용하고 각각 카드로 만든다.

**대량 덤프 처리**: 사용자가 여러 단락·문서 전체를 한 번에 붙여넣으면 "붙여넣은 단락"은 그 **전체**다. 일부만 카드로 만들고 나머지를 "다음에"로 미루는 것은 이 검증 위반이다 — 미룬 문장 = 빠진 문장. **그 응답에서 전체를 빠짐없이 담는다.** 부분 처리를 그 턴의 의무를 다한 것처럼 제시하지 않는다("나머지는 다음에"·"구획별로 나눠 진행" 금지). 구획별로 나눠 학습하고 싶으면, 이미 붙여넣은 분량은 이 턴에서 전부 담은 뒤 "다음부터 한 단락씩 붙여넣어 주세요"라고 안내한다(다음 붙여넣기부터 그 단위가 검사 단위가 된다).

도입만 해설하고 나머지를 미룬 실패(2026-07-23)로 신설한 규칙이다.

#### 1-1. 단락 요약

카드가 끝나면 단락 전체의 핵심을 비유와 함께 3줄 이내로 정리해 스펙의 `summary`에 담는다. 채팅에는 쓰지 않는다. 판정 건수는 렌더러가 `verdict`를 세어 요약 칸에 붙이므로 따로 적지 않고, 판정 목록을 다시 나열하지도 않는다 — 이미 카드마다 붙어 있다.

#### 1-2. 선택 받기

사용자가 붙여넣은 JSON이 선택 결과다. 클립보드를 뒤지지 않는다.

- 페이로드 형태: `{ __skill: "ka-digest", ts, slug, round, items: [{ i, head, verdict }] }`. `verdict`는 `save`·`explain`·`drop` 중 하나이며, 라디오를 아무것도 안 고른 문장은 `null`이다.
- **마커 확인**: `__skill`이 `ka-digest`가 아니면 다른 폼의 값이므로 쓰지 않고 "digest 페이지의 클립보드 복사를 다시 눌러 붙여넣어 주세요"라고 안내한다.
- **회차 확인**: `round`가 이번 회차와 다르면 이전 회차의 잔여이므로 쓰지 않고 "클립보드 복사를 다시 눌러주세요"라고 안내한다.
- `verdict`가 `null`인 문장이 있으면 그 문장의 `head`를 짚어 어떻게 할지 묻는다. 임의로 채우지 않는다.
- 받은 선택은 **원문과 짝지어 세션 안에 쌓아둔다.** `head`로 대조해 순서가 어긋나지 않았는지 확인한다. 이 누적이 OFF 1단계 「후보 취합」의 입력이다.
- 받은 결과는 채팅에 한 줄로만 보고한다 (예: `저장 4 · 해설 3 · 버림 9로 받았습니다. 다음 단락을 붙여넣어 주세요.`). 문장 목록을 다시 나열하지 않는다.

#### 2. 저장 판정

판정은 **카드 라디오의 기본 선택값**으로 낸다. 최종 결정은 사용자가 화면에서 하고, AI는 첫 값을 찍어둘 뿐이다. 아래 판정 기준은 그 기본값을 정할 때 그대로 적용한다.

| 판정 | 라디오 기본값 | 카드에 덧붙이는 것 |
|---|---|---|
| 새 답변의 재료 | 저장 | 없음 |
| 기존 답변에 붙일 재료 | 저장 | 의역 뒤 괄호로 `knowledge/<경로>.md`의 기존 답변에 붙인다고 한 마디 |
| explained 해설의 재료 | 해설 | 없음 |
| 아무 데도 안 남김 | 버림 | 없음 |

카드 한 장은 이렇게 생겼다 (라디오 기본값이 AI 판정):

```
Setting state only changes it for the next render.

state를 설정해도 지금 렌더의 값은 그대로고, 다음 렌더부터 바뀐다.
  next render: 이 설정이 반영되는 그다음 렌더 차례

(•) 저장   ( ) 해설   ( ) 버림      AI 판정: 저장
```

##### 「해설」 — knowledge엔 안 가고 explained로 가는 문장

세 판정은 **강도**가 아니라 **목적지**로 갈린다. 저장은 `knowledge/`의 Q&A 재료, 해설은 `explained/`의 해설 재료, 버림은 아무 데도 안 남는다. 「해설」을 "반쯤 저장"으로 읽으면 안 된다 — 애매해서 보류한 게 아니라, 갈 곳이 knowledge가 아닐 뿐이다.

「해설」이 맡는 것은 **그 자체로는 외울 게 없지만 남이 읽을 때 이해를 돕는 문장**이다.

- 앞 문장의 개념을 그대로 풀어 보이는 예시·비유
- 선행 개념에서 기계적으로 도출되는 사용 세부 (「기계적 후속은 저장하지 않는다」가 가리키는 것이 이 자리다)
- 개념의 적용 범위를 넓혀 보여주는 다른 도메인 사례 — 단, 그 사례를 **암기 대상으로 만들지 않는 선에서만**

「버림」으로 남기는 것은 문서 유지보수 배너·목차 링크·계보 귀속처럼 해설에 실어도 독자에게 아무 도움이 안 되는 문장이다.

「해설」 문장은 OFF 1단계의 질문 후보에 들어가지 않는다. OFF 2단계에서 explained 생성 에이전트에 **어느 질문의 해설에 녹일지와 함께** 넘긴다.

##### [CRITICAL] 의역 칸은 의역이지 판정 사유가 아니다

판정을 해설 줄로 합치면서 **해설 자체가 사라지는** 사고가 2026-07-25에 났다. 원문의 한글 의역이 있어야 할 자리에 "왜 제외인지"만 적힌 것이다.

- ❌ 실제 출력: `But there is one other factor at play here.` → "요인이 하나 더 있다는 전환 문장입니다."
- ✅ 있어야 했던 것: "하지만 여기에는 또 하나 작용하는 요인이 있다."
- 사용자: "해설이야 해설. 한글해설. 제안/반려 이유 적는곳이 아니란말이야."

그래서 의역 칸에는 **어떤 판정이든 반드시 그 문장의 한글 의역**이 들어간다. 버림 판정 문장도 예외가 아니다. "전환 문장입니다"·"예시입니다"·"수사적 도입입니다" 같은 **역할 라벨만 적고 끝내지 않는다** — 역할을 짚고 싶으면 의역을 먼저 쓴 뒤 뒤에 덧붙인다.

의역 자리에 **영문법을 뜯는 서술**이 들어가는 것도 같은 사고다. 2026-07-24에 났고, 사용자 지적은 "설명 양식이 왜 이러냐, 직역도 의역도 아닌 문장구조 설명이냐"였다. 무엇이 그 서술인지는 해설 가이드 §3 「영문법 구조 분석 금지」가 정본이다 — 역할 라벨과 마찬가지로, 그것을 적고 싶어도 의역이 먼저다.

##### 사유는 원칙적으로 안 쓴다

의역을 읽으면 왜 그 판정인지 대개 드러나므로, 사유를 또 적으면 같은 말을 두 번 하는 노이즈다. **아래 경우에만** 짧게 덧붙인다 — 해설 밖에서 온 근거라 의역만 봐서는 알 수 없기 때문이다.

- 기존 knowledge 파일과 중복이거나 거기에 붙일 재료일 때 (파일 경로를 적는다)
- 이 페이지가 아니라 다른 페이지·다음 절에서 다룰 범위일 때
- 앞서 저장 판정한 선행 개념에서 그대로 도출되는 내용일 때

해설 내용을 되풀이하는 사유는 쓰지 않는다. 사유를 쓸 때도 한 문장을 넘기지 않는다 — 순회는 문장 수만큼 반복되므로 사유가 길면 해설을 덮는다.

- ❌ (사례) `**제외** — Step 2의 "Rendering is React calling your components."가 같은 내용을 정의로 진술한다` → 사용자: "이렇게 쓰면 갑자기 냅다 제외? 좀더 풀어서." / `**저장**` 두 글자만 → 사용자: "저장 두글자? 무엇을 뭐 어케 저장하자는거야." 둘 다 **의역이 없어서** 판정만 덩그러니 나간 경우다.
- ✅ 교정: `<그 문장의 한글 의역> (렌더의 정의는 뒤의 Step 2가 따로 못박습니다)` — 의역이 칸의 본체를 채우고, 판정은 라디오가 지며, 밖에서 온 근거만 괄호로 짧게 붙는다.

판정에 질문 문장·중요도 라벨·제안 이유를 얹지 않는다 — 그것은 OFF 1단계의 일이다.

##### 중복 검사

판정에 앞서 **붙여넣기 1회(단락) 단위로 한 번** 수행한다. 문장 하나만 보고 판정하면 "그 문장과 뒤 문장이 합쳐져야 하나의 답이 되는" 경우를 놓치므로, 검사 단위는 문장이 아니라 단락이다.

- 태그, 파일명, 폴더 기반으로 검색
- **URL 출처 검사 ≠ 내용 중복 검사.** ON의 겹치는 것 찾아 알리기에서 URL이 무매칭이어도 중복이 없다는 뜻이 아니다 — 같은 내용이 **다른 출처 파일**에 이미 있을 수 있다(예: 한 페이지의 Service Worker 설명이 이미 `philosophy.md`에, `setupWorker`가 `quick-start` 출처의 `setup.md`에 존재). URL grep 결과와 무관하게, 중복 검사는 **개념·태그·파일명으로 별도 grep**해서 판정한다.
  - ❌ (사례) MSW browser integration(`/integrations/browser`) 단락에서 URL 출처 grep이 무매칭이자 "새 페이지 = 중복 없음"으로 판정하고 중복 검사를 생략, Service Worker 가로채기·`setupWorker`를 새 질문으로 제안 → 사용자: "기존에도 셋업관련 내용이 있었을텐데". 대조하니 가로채기는 `philosophy.md`(다른 URL) 중복, `setupWorker`는 `setup.md` 보충이었다.
  - ✅ 교정: URL 무매칭이어도 개념·태그·폴더로 knowledge를 grep해 각 후보를 신규/중복/보충으로 분류한 뒤 판정한다.
- **중복 검사는 knowledge/에 그치지 않는다 — 형제 레포 docs도 본다.** 그 주제가 MP `docs/patterns/`·`docs/best-practices/` 등에 pattern·best-practice 문서로 사는 경우 그곳도 grep한다. 특히 **테스트·컨벤션·원칙**은 KA가 아니라 MP docs에 사는 일이 많아, knowledge/만 보면 "새 질문"으로 착각한다.
  - ❌ (사례) contract("무엇을 테스트할까")·descriptive names를 knowledge/만 grep해 "KA에 없음 = 신규"로 제안 → 사용자: "MP에 있을거같은데". MP `WhatToTest.md`·`TestWriting.md`에 이미 있었다.
  - ✅ 교정: knowledge/ 무매칭이어도 MP `docs/patterns/testing`·`docs/best-practices`를 grep해 중복/보충 판정 후 진행한다.
- 기존 Official Answer와 **완전히 동일한 문장**이면 `제외`
- **같은 개념이지만 다른 출처의 다른 표현**(더 쉬운 설명, 다른 관점, 보충이 되는 문장)이면 `제외`가 아니라 `저장(보충)`

**단, 위 두 줄은 이번 문서 기준으로 다시 쓸 일이 없는 파일과 겹칠 때만 적용한다.** ON에서 알린 겹침 목록에 있고 이번 재료가 그 내용을 대체·개정하는 파일이면 중복이 아니라 **갈아끼울 자리**이므로 「저장」으로 판정한다. 그 파일은 어차피 다시 쓸 거라, 거기 같은 문장이 이미 있다는 건 버릴 이유가 못 된다.

이걸 빼먹으면 조용히 손해가 난다. 새로 읽은 문장이 옛 파일에 있던 문장과 같다는 이유로 「버림」이 찍히고, 「필터링」의 "순회 중 버림으로 정해진 문장은 여기서 되살리지 않는다"에 걸려 **다시 쓴 파일에 구멍이 뚫린다**.

정본 통합(SSOT) 방향 결정 — 어느 파일을 정본으로 삼고 어느 쪽이 참조할지 — 은 질문이 확정돼야 판단할 수 있으므로 여기서 하지 않는다. **OFF 1단계로 넘긴다.** 대신 관련 기존 파일 경로를 `저장(보충)` 판정에 적어두어, OFF에서 다시 검색하지 않아도 되게 한다.

##### `제외` 판정 기준

기본은 **"알 필요가 없는 내용"**이다 (하드웨어 표준 세부사항, 관리 체계 등). **"쉬운 내용", "이미 알 만한 내용", "상식"은 제외 사유가 아니다** — 알아야 하는 내용이면 난이도와 무관하게 저장한다. **"나중에 더 자세히 배울 것 같다"도 제외 사유가 아니다** — 필요한 내용이면 지금 저장하고, 나중에 깊이 배우면 그때 분리하거나 보충한다. 최종 판단은 사용자가 한다 — 판정을 보고 사용자가 뒤집으면 그대로 따른다.

**사용자 역할 기준 필터링**: 사용자의 역할·배경(예: 프론트엔드 개발자, AI 사용자)이 명확하면 그 역할과 무관한 전문 분야 내용은 기본 제외 후보로 분류한다.
- 비개발 도메인 적용 사례(의료·반도체·물류 등) → 개발자 사용자에게 제외
- 구현·운영 레벨 세부사항(모델 내부 회로, 인프라 설계 등) → 일반 사용자·소비자 역할에게 제외

**상대편이 쓰는 API는 내 코드가 달라질 때만 저장한다**: 사용자의 역할이 한쪽(웹)인데 문서가 양쪽(웹·앱, 프론트·백엔드)을 함께 다루면, 상대편이 부르는 이름 자체는 저장하지 않는다. 가르는 것은 **그것 때문에 내 쪽 코드가 달라지는가**다. 달라지면 저장하되 질문은 내 쪽 결과를 묻는 각도로 세우고, 안 달라지면 해설로 내린다. 바로 위 「사용자 역할 기준 필터링」이 도메인이 아예 다른 경우를 잡는다면, 이 축은 같은 화면을 함께 만드는 상대편을 잡는다.

- ❌ (사례) react-native-webview 가이드에서 `injectedJavaScript`·`injectedJavaScriptBeforeContentLoaded`·`injectedJavaScriptObject`를 각각 톱레벨 질문으로 제안 → 사용자: "저거 전부 RN 개발하는 사람이 해야 하는 거 아니야? 웹개발자가 이걸 알아야 할 이유가 뭐야?"
- ✅ 교정: 셋 중 웹 코드를 실제로 가르는 것(값을 로드 전에 심었는지 후에 심었는지)만 남기고, 질문은 "앱이 심어준 값을 웹이 번들 최상단에서 바로 읽어도 되는가"로 각도를 돌린다. prop 이름 자체를 묻는 질문은 세우지 않는다.
- **그 API가 왜 생겼는지의 플랫폼 사정**(안드로이드 경합 등)도 같은 축에서 버림이다. 상대편 사정이라 내 코드를 안 가른다.

**이론적 타당 ≠ 실무 빈도**: 1차 소스 근거가 있어 이론적으로 타당해도, 사용자의 역할·실무 맥락에서 실제로 마주칠 **빈도가 낮은** 내용은 제외 후보다 (위 역할 필터링이 "도메인 불일치"를 잡는다면, 이건 도메인 안에 있으면서도 그 하위 맥락에서 드문 경우를 잡는다). 단, "실무 빈도 낮음"을 사유로 적을 때는 **왜 낮은지 납득 가능한 메커니즘을 반드시 함께 적는다** — 단순 단정("이건 실무에서 잘 안 써요") 금지.
- ❌ (사례) stale mock을 Fowler 1차 소스라는 이유로 실무 빈도 검토 없이 바로 저장 → 사용자가 "공개 API는 breaking change를 v2로 빼지 v1을 안 바꾼다"며 전량 롤백.
- ✅ 교정: 의역 뒤에 메커니즘을 짧게 덧붙이고 기본값을 버림으로 둔다 — `<한글 의역> (공개 API는 breaking change를 v2로 분리하고 v1을 유지하므로 프론트가 마주칠 일이 드뭅니다)`.

**기계적 후속은 knowledge에 저장하지 않는다**: 같은 페이지에서 이미 「저장」으로 정한 개념에서 **기계적으로 유추되는 API 사용 세부**(값을 어디서 꺼내는지, 옵션을 어느 인자에 얹는지 등)는 Q&A로 만들지 않고 「해설」로 정해, OFF에서 선행 질문의 해설에 흡수한다. "그 개념을 알면 이건 굳이 외울 게 아니라 그때 찾아보면 되는가?"가 예이면 카드가 아니라 레퍼런스다. "쉬운 내용은 제외 사유 아님"과 구분되는 지점 — 여기서 knowledge에 안 넣는 사유는 난이도가 아니라 **선행 개념에서의 도출 가능성**이다.
- ❌ (사례) `:id`로 경로 파라미터를 이름 붙이는 걸 저장한 뒤, "resolver에서 그 값을 `params`로 꺼낸다"를 별도 질문으로 제안 → 사용자 반려. `HttpResponse`를 저장한 뒤 "status·headers는 둘째 인자 옵션에 얹는다"를 별도 질문으로 제안 → 사용자 반려. 둘 다 선행 개념에서 바로 유추되는 사용 세부다.
- ✅ 교정: `<한글 의역> (앞의 <개념>에서 도출되는 사용 세부라 explained 해설로 흡수합니다)`로 쓰고 기본값을 「해설」로 두어, OFF에서 그 선행 질문의 해설에 한 줄로 녹인다.

**계보는 빼고 효용·지침은 남긴다**: 개념이 언제 누구에게서 나왔는지, 몇 가지 형태로 분류되는지, 어느 책·논문에 실렸는지, 사용자 도메인 밖에서 어떻게 쓰이는지는 제외한다. 그것으로 **무엇이 좋아지는지**, **무엇을 하라는 건지**, **그 대가로 무엇을 치르는지**는 저장한다. 같은 개념을 다룬 두 문서에서 판정이 정반대로 빗나간 뒤 남은 축이다 — 가르는 것은 형식(나열이냐 산문이냐)이 아니라 그 문장이 독자를 판단·행동하게 만드는가다.

- ❌ (사례) 위키백과 관심사 분리 문서에서 Dijkstra 1974·Chris Reade 1989 귀속, 관심사 분리 형태 4분류, 프로토콜 계층·관점 지향 프로그래밍·AI 분석 수준 적용 사례를 저장으로 판정 → 사용자가 전부 반려. "내가 저걸 암기해야할 이유가없어" / "다른 사례 외울필요없어."
- ❌ (사례) 반대 방향으로, GeeksforGeeks 관심사 분리 문서의 이점 목록·함수 적용 기법·설계 적용 기법을 제외로 판정 → 사용자: "아니; 전부다 대부분이 저장할 얘기인데? ... 이건 구체적인 솔루션이기까지 한데?"
- ✅ 교정: 계보·분류·타 도메인 사례는 제외하고, 효용·지침·비용은 저장한다.

#### 출력 규칙

중복 검사·니치 분류 등의 **판단 과정**은 내부적으로 수행하되 사용자에게 보여주지 않는다. 사용자에게 나가는 것은 브라우저 페이지의 카드(인용·의역·영단어 해설·라디오)와 하단 단락 요약뿐이고, 채팅에는 페이지를 열었다는 안내와 받은 결과 한 줄만 남는다.

### OFF 1단계 — 질문 확정·저장

페이지 순회가 끝나고 사용자가 `OFF`를 입력하면 여기서 시작한다.

#### 후보 취합

회차마다 받아 쌓아둔 선택에서 **「저장」으로 표시된 문장**을 모두 모은다 (「1-2. 선택 받기」의 누적). 순회 중 페이지에 verbatim으로 실어둔 원문을 그대로 쓴다 — 기억을 더듬어 재구성하거나 문장을 새로 짓지 않는다.

「해설」로 표시된 문장은 질문 후보가 아니므로 여기서 모으지 않는다. 대신 **어느 질문의 해설에 녹일지**를 정해 따로 묶어두고, OFF 2단계의 explained 생성 에이전트에 넘긴다.

해설 과정에서 도출된 통찰(왜 이런 설계인가, 기존 방식과의 차이, 실무적 의미 등)도 질문 후보로 함께 검토한다. 통찰에 대응하는 영어 원문을 Official Answer로, 통찰 자체는 OFF 2단계에서 생성하는 explained/ 섹션에 보충으로 기록한다.

#### 파일마다 어떻게 할지 정하기

ON에서 겹침 목록에 오른 파일이 있으면, 파일마다 아래 셋 중 하나로 정해 확인받는다. **이 절차가 보충 검토·정본 통합보다 먼저 온다** — 어차피 지울 파일을 보충하거나 정본으로 삼는 헛일을 막기 위해서다.

| 어떻게 | 언제 | 무엇을 하는가 |
|---|---|---|
| 통째로 다시 쓰기 | 문서가 개정돼서 기존 내용 대부분이 지금과 다름 | 파일을 지우고 이번 재료로 새로 쓴다 |
| 일부만 갈아끼우기 | 일부 질문만 낡음 | 낡은 Q&A만 지우고 나머지는 둔다 |
| 그대로 두기 | 이번 문서가 그 부분을 다루지 않음 | 손대지 않는다 |

- **파일 나눔을 이번 문서에 맞춘다.** 기존 파일명·폴더가 이번 문서의 짜임새와 안 맞으면 쪼개거나 합치거나 옮긴다. 기존 배치에 억지로 끼워 넣지 않는다. 옮기거나 이름을 바꿀 때는 `explained/`·`assets/`의 같은 경로도 함께 옮긴다.
- **짝 파일도 같이 지운다**: knowledge 질문·파일을 지우면 `explained/`·`assets/`의 같은 자리도 지운다. 저장이 끝나면 `/validate`로 남은 것을 정리한다.
- 범위 밖 파일은 이 절차의 대상이 아니다. 건드릴 일이 생기면 사용자에게 알리고 범위에 넣을지 확인받는다.

#### 기존 답변 보충 검토

`저장(보충)` 판정된 재료를 처리한다. 새 질문을 만들기 전에, 그 내용이 기존 Q&A의 답변을 보강할 수 있는지 검토한다.

- **다른 출처의 Official 원문**이 기존 Official Answer와 같은 개념을 다른 표현·각도로 설명하면, 기존 OA에 단락으로 이어 붙이는 보충을 적극 제안한다. 새 출처 URL은 Reference 섹션에 추가한다 (OA 본문에 인라인 URL을 박지 않는다 — [content-format.md](../../contexts/content-format.md)의 "출처 표기는 Reference에만" 참고).
- 기존 답변에 구체적 예시·안티패턴 등 비공식 보충이 필요하면 explained/ 보충을 제안한다. OFF 2단계에서 생성하는 explained/ 섹션에 반영한다.
- 새 질문으로 만들 만큼 독립적이지 않지만, 기존 답변을 풍부하게 만드는 내용이 대상이다.
- **기존 OA에 보충하면 대응 explained도 함께 갱신한다.** explained 생성은 OFF 2단계에서 신규 질문만 배치 처리하므로, 기존 질문의 OA에 단락을 append하고 explained를 두면 그 질문의 explained 섹션이 옛 내용에 머문다(knowledge↔explained drift). 해당 explained 섹션이 이미 있으면 OFF 2단계의 갱신 대상에 반드시 포함시킨다.
  - ❌ (사례) `mocking.md` "언제 mocking" OA에 Vitest 판별 기준을 append한 뒤 explained 미갱신 → 사용자: "니가 실수한건 explained 하고 해".
  - ✅ 교정: OA append와 같은 세션에 `explained/frontend/testing/mocking/overview.md`의 해당 섹션도 동기화.

#### 정본 통합 (SSOT) 판단

**겹침을 찾으면 복사본을 병렬로 두지 말고, 정본(SSOT 원본) 하나로 몰고 나머지는 참조한다.** 같은 개념이 여러 파일(형제 레포 docs 포함)에 흩어져 있으면 한 곳으로 통합하고, 다른 쪽은 그 질문을 참조하도록 바꾼다. 신규 저장뿐 아니라 기존 문서를 손볼 때도 적용된다. (한 주제를 여러 URL로 digest하면 파일 간 질문 중복이 필연적으로 생기므로, 이 분기가 정기적으로 걸린다.)

- **지우기로 한 파일은 정본 후보에서 뺀다.** 이 절의 기본값은 "기존 파일 쪽으로 몰기"인데, 그 파일이 이번에 갈아엎을 대상이면 낡은 쪽을 정본으로 세우는 꼴이 된다. 갈아엎기로 한 파일이 있으면 이번에 새로 쓰는 파일이 정본이다.
- **개념 vs 그 구현(API)**이 겹치면 항상 **개념 쪽에 통합**하고 API 쪽은 참조한다.
- 통합할 때 다른 파일에만 있던 측면(정본에 없던 각도·예시)도 함께 흡수한다.
- **OA 병합은 문장 통째 단위로**: 서로 다른 출처의 OA 문장을 통째로 골라 잇는 건 허용하되, **문장 내부의 단어를 섞어 문장을 재작성하지 않는다** (content-format.md의 「원문 보존」·「OA 단락 통합」과 같은 선 — 원문 문장은 그대로 둔다).
- **참조 형식**: 참조하는 쪽은 대상 파일의 해당 질문을 마크다운 링크로 가리킨다 — `[상대경로](상대경로)의 「질문 제목」`. (seam 작업에서 `mocking.md`가 `philosophy.md`의 질문을 가리킨 방식이 예.)
- 참조할 건덕지조차 부족하면(정본이 될 쪽이 질문 1개뿐 등) 참조를 남기지 말고 **한쪽으로 완전히 통일**한다.
- ❌ (사례) `mocking.md`와 `msw/philosophy.md`에 "fetch를 통째 mock하면 잘못된 요청도 통과한다"가 각각 풀려 병렬 존재 → 사용자: "내가 원하는건 SSOT야. 한곳에 몰아두고 그걸 참조하게끔."
- ✅ 교정: 개념(요청 조립 이음새)을 `philosophy.md` 정본으로 통합하고, `mocking.md`는 상위 일반 원칙만 남긴 뒤 그 정본을 참조.

#### 질문 제안

취합한 재료로 질문을 제안한다. 질문은 아래 **① 유형**에서 골라 **② 작성 원칙**으로 다듬고 **③ 배치·위계**로 배열하며 **④ 필터링**으로 취사한다.

- **여러 각도로 제안**: 하나의 답변·개념도 ① 유형(정의·오개념·실무 연결·문제→해결·예시)의 서로 다른 각도로 제안할 수 있다. AI가 한 각도로 스스로 좁히지 않는다 — 각도가 유용하면 복수로 내놓고, 어느 각도로 갈지 취사는 사용자에게 맡긴다.
  - **단, primary는 담백한 정의·이유형으로.** 복수 각도를 낼 때도 첫 제안(primary)은 개념을 곧이곧대로 묻는 정의/이유 질문으로 하고, 오개념·실무연결 등 영리한 각도는 보조로 붙인다. primary 자리에 오개념 타파나 '다각도 메뉴'를 앞세우지 않는다.
- **각도 2회 반려 시 묻기**: 제안한 질문 각도를 사용자가 2회 이상 반려하면, 새 각도를 추측으로 더 던지지 말고 "어떤 각도·답변을 원하는지" 사용자에게 묻는다 (글로벌 「루프 감지」의 digest판).
  - ❌ (사례) act() 렌더 질문에서 effect-반영/오개념 각도를 2회 반려당한 뒤, 묻지 않고 4개 각도(A~D) 메뉴를 더 던짐 → 사용자: "에휴 그냥 담백한 각도로". 2회 반려 후엔 각도를 더 생성하지 말고 물었어야 했고, 애초 primary를 담백한 정의형("왜 act로 감싸는가")으로 냈어야 했다.

**① 질문 유형 (메뉴)**
- 일반 질문: "X란 무엇인가?"
- 오개념 타파: "X는 Y를 하는가?" (답이 아니오인 질문)
- 실무 연결: "X가 실제로 해결하는 문제는?"
- 문제→해결: "이런 문제가 있었다. 어떻게 해결하는가?" (recall에 좋다)
- **예시 해석**: 재료에 실제 코드/설정/프로토콜 예시가 포함된 경우, 예시를 질문 본문에 그대로 싣고 "각 부분의 역할을 설명하라" 형태로 만든다. 복습 시 예시를 보고 직접 해석한 뒤 답을 확인하는 훈련이 된다.

**② 작성 원칙 (recall 품질)**
- **면접 질문처럼**: 맥락 없이 읽어도 무슨 말인지 이해되어야 한다. 전문 용어로 냅다 시작하지 말고, 상황/배경을 질문 안에 포함한다.
- **개념이 주어면 이름을 대고 묻는다 (수수께끼 금지)**: 질문 대상이 특정 API·개념이면 그 이름을 질문에 그대로 쓰고 곧이곧대로 묻는다. 위 "면접 질문처럼(상황/배경 포함)"은 맥락을 주라는 것이지, 대상 이름을 숨기고 상황만으로 그게 뭔지 맞히게 하라는 게 아니다. 상황 서술은 후보가 여럿이라 가려야 할 때(모호성 제거)만 쓴다.
  - ❌ (사례) "각 테스트를 특정 문맥으로 감싼 채 실행해야 할 때 쓰는 훅은?" → 답인 `aroundEach`를 상황으로 에둘러 맞히게 함. 사용자: "수수께끼 극혐. 수수께끼 자체를 하지마."
  - ✅ 교정: "aroundEach 훅은 무엇을 하며, 어떻게 동작하는가?" — 대상 이름을 대고 담백하게.
- **정답 키워드 누설 금지**: 사용자가 떠올려야 할 답의 핵심 요소(반환값의 필드명·구성 요소·용어 등)를 질문 문장에 미리 적지 않는다. 키워드를 질문이 불러주면 recall 훈련이 무력화된다. 막연히 묻고, 그 키워드 산출을 사용자 몫으로 남긴다.
  - ❌ "next()는 무엇을 반환하며 `value`·`done`은 각각 무슨 의미인가?" → 답인 `value`·`done`을 질문이 미리 노출
  - ✅ "next()는 무엇을 반환해야 하며, 그 반환 객체 안의 필드들은 각각 무엇을 의미하는가?" → 사용자가 `value`·`done`을 스스로 떠올려 설명
  - 단, 그 용어 자체가 답이 아니라 질문의 **전제·상황**일 때는 언급해도 된다.
- **리스트 암기 금지**: "3가지는?", "핵심 특성은?", "장단점은?" 식의 나열 질문 금지. 사용자에게 키워드 목록을 외우라는 꼴이 된다. 대신 각 항목을 개별 질문으로 분리하거나, 질문에 키워드를 언급하여 이해를 묻는 형태로 만든다.
  - ❌ "BST의 핵심 특성은?" → 사용자가 Ordering Property, Recursive Nature, No Duplicates... 를 줄줄 외워야 함
  - ✅ "BST에서 왼쪽 서브트리와 오른쪽 서브트리의 값은 어떤 관계인가?" → 키워드(ordering property)를 이해하고 설명하는 질문
  - **비교·선택 프레이밍도 리스트 암기일 수 있다**: "A·B·C 중 무엇을 택하나" 같은 비교/결정형이라도, A·B·C가 굳어진 명칭이 아니라 그 문서 안에서만 등장한 임시 분류면 결국 그 목록을 통째로 떠올리라는 리스트 암기다. "담백한 primary"로 위장되지 않으니, 임시 분류는 지우고 단일 개념만 담백하게 묻는다.
    - ❌ (사례) 훅 테스트 글에서 "세 방식(실제 예제 컴포넌트 / UI 없는 helper / renderHook) 중 저자는 무엇을 택하나?"를 담백 primary로 제안 → 사용자: "담백이 아닌데? 냅다 배경지식 없는 상태에서 세 방식을 암기하라고? 유명한 명사도 아니고." → 교정: 임시 3분류를 지우고 "renderHook은 어떤 문제 때문에 등장했나" 단일 개념만 물음.
- **질문 문장에 코드 호출을 인라인하지 않는다**: `renderHook(...)`처럼 코드를 질문에 그대로 박아 "이걸 읽어보라"는 식으로 쓰지 않는다. 면접관이 코드를 소리 내어 읽어줄 수 없듯, API를 물으려면 이름을 대고 "~의 시그니처를 설명하라"처럼 묻는다. (예외: ① 유형의 **예시 해석**은 코드를 의도적으로 싣고 "각 부분의 역할을 설명하라"는 것이므로 여기 해당하지 않는다.)
  - ❌ (사례) 질문에 `renderHook(callback, options)`를 그대로 박고 반환을 물음 → 사용자: "질문에서 코드는 절대 쓰면안돼. 차라리 renderHook() 시그니처 뭔지 설명하라고 하는 게 낫겠다."
  - ✅ 교정: "renderHook()의 시그니처(인자·반환)를 설명하라." — 이름을 대고 설명을 요구.
- **결론(verdict)을 사실로 암기시키지 말고, 그 결론이 도출되는 원리를 묻는다**: KA는 판정을 외우는 곳이 아니라 이해하는 곳이다. "A가 B보다 낫다/우선한다" 같은 결론 자체를 확인하는 질문 대신, "왜 그런가"를 물어 사용자가 원리로 재구성하게 한다.
  - ❌ "renderHook()보다 render()를 우선시하는가?" → "우선시한다"는 결론만 떠올리면 끝
  - ✅ "재사용 훅을 renderHook 대신 실제 컴포넌트로 렌더해 테스트하면 어떤 차이가 생기는가?" → 우열을 전제하지 않고 원리(실제 사용에 가까움)를 스스로 세우게 함

**③ 배치·위계**
- **정의 먼저**: 재료에 정의·사용법·비교·응용이 함께 있으면 정의 → 사용법 → 비교/응용 순으로 제안한다. 비교·응용·오개념 타파 질문은 같은 주제의 정의 질문이 모두 제안된 뒤에만 낸다. 새 개념(예: subagent, agent team)이 처음 등장하면 "X란 무엇인가?" 정의 질문을 반드시 먼저 낸다.
  - ❌ (사례) API/RESTful 단락에서 정의 질문 없이 "REST와 일반 API 차이?" 같은 비교 질문부터 제안 → 사용자 지적: "각 개념을 먼저 확정하고 그런 질문을 던지는 게 좋지 않나?"
- **정론 먼저, 꼬리질문은 그 다음**: 먼저 개념 자체를 담백하게 묻는 질문(정론)을 만들고, 그 안에서 꼬집을 세부를 꼬리질문으로 붙인다. 오개념 타파 질문을 억지로 만들지 않는다 — 정론이 있어야 꼬리질문이 의미가 있다.
- **위계 구조 일관성**: 사용자가 "톱레벨 + 꼬리질문" 위계를 확립·요구하면 이후 제안도 같은 위계로 구성한다. 질문이 5개 이상 나올 것 같으면 flat 대신 톱레벨 + 꼬리 위계를 기본으로 한다.
  - ❌ (사례) 1단락에서 위계를 세운 뒤 2단락에서 flat 8개로 회귀 → 사용자 지적: "큰 범위 먼저 묻고 꼬리질문 여러 개로 구조화하자. 아까처럼."
- 부모 질문과 꼬리질문의 Official Answer는 내용이 겹쳐도 괜찮다. 단, 완전히 동일한 복붙은 피한다.
- **한 질문에 물음이 둘이면 쪼갠다**: 질문 문장 안에 독립적으로 답할 수 있는 물음이 2개 이상 들어 있으면 각각 별도 질문으로 나눈다("1개로 줄여라"가 아니라 "각각 1개씩으로 나눠라").
  - ❌ (사례) "beforeEach·afterEach는 각각 언제 실행되며, 실패해도 afterEach는 도는가?" → 실행 시점 + 실패 시 동작, 두 물음이 한 질문에
  - ✅ 교정: "beforeEach·afterEach는 각각 언제 실행되는가?" / "테스트가 실패해도 afterEach는 실행되는가?" 두 질문으로 분리
- **과분할된 중복 질문은 흡수하거나 삭제한다 (억지 흡수 금지)**: 거의 같은 걸 묻는 질문이 여러 개로 쪼개져 답이 대부분 겹치면 한 질문에 흡수한다. 흡수할 실질 내용이 없으면 억지로 합치지 말고 삭제한다. 단, 정당한 부모-꼬리 위계(위 규칙)는 흡수 대상이 아니다 — 위계 없이 같은 층위에서 거의 같은 걸 묻는 형제 질문만 대상이다.
  - ❌ (사례) 렌더된 컴포넌트에 이벤트를 발생시켜 결과를 검증하는 방법을 둘째·셋째 질문으로 나눠 물어 답이 거의 겹침 → 사용자: "하나로 두 답변을 다 유도할 수 있나"
  - ✅ 교정: 한 질문으로 흡수하거나, 흡수할 게 없으면 잉여 질문 삭제
- **페이지 전체를 놓고 배열한다**: 순회가 끝난 뒤 뽑으므로 페이지 앞뒤의 재료가 한자리에 있다. 앞부분 문장과 뒷부분 문장이 하나의 답을 이루면 **한 질문으로 합친다** — 등장 순서대로 따로 세우지 않는다. 이 이점을 쓰라고 질문 뽑기를 순회 후로 미룬 것이다.

**④ 필터링**

- **중요도 사전 판단 (내부 전용)**: 질문을 제안할 때, 출처의 성격에 따라 적절한 중요도 기준을 적용하여 **내부적으로** 필터링한다. 중요도 라벨은 사용자에게 **보여주지 않는다**.
  - **라이브러리/프레임워크 공식문서**: "핵심 API" (거의 매번 쓰는 기능), "자주 사용" (알아두면 유용), "고급/니치" (특수 상황에서만 필요) 로 구분한다.
  - **CS 개념/이론 문서**: "면접 핵심", "CS 배경지식", "니치/선택" 으로 구분한다.
  - 출처 URL의 도메인과 경로(예: `/docs/`, API 레퍼런스 등)로 자동 판단한다. 판단이 애매하면 사용자에게 확인한다.
  - 중요도가 섞여 있으면 핵심만 기본 제안하고, 나머지는 선택으로 분리한다.
  - **제안 전 자기 검증**: 각 질문에 대해 아래를 자문한다: (1) "이걸 알면 사용자가 뭘 새로 할 수 있는가?" — 새로운 기능/패턴/가능성이 열리는 내용을 우선 제안한다. (2) "이걸 몰랐을 때 실무에서 어떤 문제가 생기는가?" — 답이 약하면 니치로 분류한다. 니치 항목은 기본 제안에서 제외하고, 사용자가 요청할 때만 제안한다.
- **판단 근거를 먼저 낸다**: 한 페이지에서 뽑을 질문이 여럿이면, 그 도구·개념을 **쓸지 말지 / 어느 쪽을 고를지를 가르는 근거**를 담은 질문을 앞에 세운다. 동작 서술("이렇게 동작한다")·통과 규칙 같은 설명형은 그 뒤에 붙이고, 자리를 못 얻으면 explained 해설로 보낸다. 설명형을 빼라는 게 아니라 순서 이야기다 — 사용자가 이미 익숙한 주제일수록 설명형은 반려되고 판단 근거형만 남는다.
  - ❌ (사례) context 페이지에서 중간 컴포넌트 통과·context끼리 독립·읽으며 다시 제공을 각각 질문으로 제안 → 전부 삭제당함. 살아남은 넷은 prop drilling이 왜 생기는가, context가 무엇을 가능하게 하는가, 가장 가까운 제공자가 이긴다, context의 단점이었다. → 사용자: "판단근거는 아주 높은확률로 채택될거야."
  - ✅ 교정: 단점·비용·선택 기준·오개념 교정을 먼저 배열하고, 동작 서술은 해설로 흡수한다.
- 순회 중 「버림」·「해설」로 정해진 문장은 여기서 질문으로 되살리지 않는다. 되살릴 근거가 생겼으면 그 사실을 사용자에게 알리고 확인받는다.

#### 제안 출력 포맷

질문을 제안할 때 사용자에게 보여주는 것은 **아래가 전부**다:

1. **한글 질문**: 저장될 질문 문장
2. **한글 해설**: 질문에 대한 답의 핵심을 한글로 풀어 설명 (영어 원문 번역 + 요지). 저장 시 Official Answer가 될 영어 원문은 **이 단계에서 보여주지 않는다** — AI가 해설 작성의 근거로 내부 보관만 한다.
3. **제안 이유**: 이 질문을 왜 제안했는지 한 줄 (recall 가치, 실무 활용, 오개념 교정 등 구체적으로)

**보여주지 않는 것 (내부 처리)**:
- 영어 원문 (Official Answer 후보) — 번역해서 해설로만 노출
- 중요도 라벨 — 내부 필터링에만 사용
- 작업용 내부 라벨·약칭(`Q1`/`(A)`/`primary` 등) — 가리킬 대상을 풀어 쓴다 ([explanation-guide.md](../../contexts/explanation-guide.md) §3 「작업용 내부 라벨·약칭 노출 금지」)

사용자가 승인하면 아래 **승인 시 저장** 절차를 실행한다. 거부하면 버린다.

**보류·반려된 질문의 꼬리질문은 함께 보류한다.** 사용자가 톱레벨 질문을 보류·반려하면 그 아래 꼬리질문도 같은 처분으로 묶는다. 사용자가 꼬리질문을 따로 언급하지 않았다는 이유로, 또는 "나머지는 전부 승인" 같은 포괄 승인에 묶인다는 이유로 승인으로 취급하지 않는다. 어느 꼬리가 함께 빠졌는지 보고만 하고 끝낸다 — 살릴지 되묻지 않는다.

- ❌ (사례) 「props가 바뀌는 횟수를 줄이는 설계」를 사용자가 보류한 뒤, 그 꼬리인 「함수를 prop으로 넘겨야 하면」을 "언급 없음 = 승인"으로 읽고 저장 → 사용자: "내가 반려한것도 들어가있네".
- ✅ 교정: 부모가 보류·반려면 꼬리도 저장하지 않고, 함께 빠졌다는 사실만 보고한다.

#### 승인 시 저장

- [production-guide.md](../../contexts/production-guide.md)의 **After** 전체 실행 (파일 배치, 구조 검증, 태그 검증)
- 대상 파일을 결정하고 Q&A를 작성하여 저장한다. 기존 파일에 추가하는 경우 Questions 목록과 Answers 섹션 양쪽에 넣는다.
- 주제가 여러 파일로 갈리면 각각 파일 배치를 결정한다.

**Official Answer는 순회 페이지에 verbatim으로 실어둔 원문을 그대로 옮긴다.** 기억을 더듬어 재구성하거나 문장을 새로 짓지 않는다 — 순회 단계가 모든 문장을 verbatim 인용해두는 이유가 여기에 있다. 인용해둔 것과 다른 문장이 필요하다고 느끼면, 그건 OA가 아니라 해설이므로 explained로 보낸다.

- **knowledge OA를 저장하면 explained 짝의 존재·정합을 이 시점에 확인한다.** `knowledge/<rel>.md`에 질문을 추가했으면 `explained/<rel>.md`의 대응 섹션이 있어야/맞아야 한다는 확인을 미루지 않는다(신규 질문의 explained 본문 작성 자체는 OFF 2단계에 맡기더라도, 짝 확인은 지금 한다).

**지운 게 있으면 커밋을 둘로 나눈다.** **지우기만 담은 커밋을 먼저** 쌓고, 그 위에 새로 쓴 커밋을 올린다. 한 커밋에 섞으면 무엇이 사라졌는지가 새로 추가된 줄에 묻혀 사용자가 diff로 판단할 수 없다.

짝 파일(`explained/`·`assets/`) 삭제는 knowledge 삭제와 같은 커밋에 넣는다 — 짝이 깨진 중간 상태를 히스토리에 남기지 않기 위해서다.

저장이 끝나면 사용자 개입 없이 아래 2단계로 이어간다.

---

### OFF 2단계 — 산출물 생성

1. 이번 세션에서 변경한 knowledge 파일 목록과 요약(새 질문 N건, 보충 N건)을 보고한다
2. **priority 확인**: 1에서 보고한 파일 각각에 대해 frontmatter `priority`를 어떻게 할지 사용자에게 묻는다. 값(`1`/`2`/`5`/빈 값)의 의미는 [content-format.md](../../contexts/content-format.md)의 `priority` 참고 — **AI는 값을 추측해 채우지 않는다**, 사용자가 답한 값 그대로 반영한다. 신규 생성 파일뿐 아니라 기존 파일에 질문을 추가·보충한 경우도 대상이다(이미 값이 있으면 유지할지 바꿀지 함께 묻는다).
3. **explained 생성 — 별도 에이전트 위임**: 아래 정보를 구성하여 별도 에이전트에 전달하고, 에이전트가 `explained/<rel>.md`를 작성하게 한다. 에이전트는 이 세션의 대화 맥락을 직접 보지 않으므로, 세션 지칭 표현 없이 독자 관점으로 explained를 생성한다.

   **에이전트에 전달할 내용 (세션 요약):**
   - 대상 파일 경로: `explained/<rel>.md`
   - 확정된 질문 목록 (OA 원문 포함)
   - 질문별 사용자 오해·막힌 지점·재설명 내용 — 세션 맥락 표현 없이 **사실만** 요약 (예: "사용자가 collapse와 collision의 차이를 혼동했다. collapse는 여럿이 하나로 줄어드는 것이고 collision은 둘이 부딪혀도 둘이 유지된다는 점을 재설명했다")
   - OFF 1단계에서 기존 OA를 보충한 질문이 있으면 그 explained 섹션도 갱신 대상으로 함께 전달
   - 「해설」로 표시된 문장들 — 원문 인용과 한글 의역을 그대로 넘기고, 각각 **어느 질문의 해설에 녹일지** 짚어준다 (「후보 취합」에서 묶어둔 것)
   - 데모·이미지 등 생성한 자산 경로 (있으면)
   - 적용 규칙: [explanation-guide.md](../../contexts/explanation-guide.md) (§6 저장 위치·섹션 순서·소유권 포함)

   **에이전트 지시:**
   - 각 질문에 대해 `# <질문>` H1 + `## 도입` / `## 본문` / `## 종합` 양식으로 explained 섹션 작성
   - 이미 있는 섹션은 덮어쓰지 않고 보존 (단, 위에서 갱신 대상으로 지정한 섹션은 예외)
   - 이번에 knowledge를 다시 쓰거나 갈아끼운 질문은 기존 explained 섹션을 **덮어쓴다** (「해설은 knowledge에 저장하지 않고, explained로 보낸다」의 소유권 예외). 어느 섹션이 여기 해당하는지 에이전트에 짚어서 전달한다.
   - 데모·이미지 자산은 `assets/<rel>/`에서 explained 본문으로 상대 경로 링크
4. **explained 표현 다듬기 — `/write-refine`**: 3에서 작성·갱신된 explained 섹션에 `/write-refine`를 실행해 톤·표현을 다듬는다. AI가 처음 뽑은 어색한 문장이 그대로 커밋되지 않게 하는 후처리다.
   - 표현만 다룬다 — 사실·내용·구조(`# <질문>` H1 + `## 도입`/`## 본문`/`## 종합`)는 바꾸지 않는다.
   - `>` 블록쿼트로 인용된 영어 원문은 손대지 않는다 ([explanation-guide.md](../../contexts/explanation-guide.md) §1의 원문 인용).
5. **소스 충실도 검증 — 별도 에이전트 위임 (explained 생성과 독립)**: explained 생성 에이전트가 자기 근거를 자가채점하지 않도록, 3과 **별개의** 검증 에이전트에 위임한다. 위반은 사용자에게 경고로 보고하고, 수정 여부는 사용자가 판단한다.

   **대상**: 이번 세션 diff에서 **추가·수정**된 Q&A 중 `source: official`이고 Reference URL이 있는 것. 신규 질문뿐 아니라 기존 OA를 수정·보충한 질문도 포함한다 (수정도 개작일 수 있다).

   **OA↔Reference 대조** ([content-format.md](../../contexts/content-format.md) §0 「원문 보존」·§3 「`Official Answer`는 예외 없이 수정 금지」, 위 「내용 분류」의 원문 합성 금지):
   - 각 Q&A의 Reference URL(들)을 WebFetch로 가져와, OA의 각 영어 문장이 원문에 **verbatim substring**으로 존재하는지 대조한다.
   - 매칭은 **문장 단위**다 — 서로 다른 출처·위치의 원문 문장을 그대로 이어 붙이는 것은 허용 정책이므로, 블록·단락 단위로 대조하면 정상 이어붙임이 오검출된다.
   - 어느 Reference 원문에서도 못 찾은 문장은 **"원문 불일치" 경고**로 보고한다 (개작·합성·환각 후보).

   explained 본문에 원문 인용이 아예 없는 경우는 여기서 보지 않는다 — `npm run validate-lint`가 레포 전체를 그 눈으로 훑는다. 에이전트에 맡기면 이번 세션에 만진 질문만 보게 되어 예전에 샌 것은 영영 안 걸린다.

   **verdict 규칙 (환각 방지)**:
   - "일치" verdict마다 매칭된 소스 원문 문장을 **인용**한다 — 인용 없는 "verified"는 무효.
   - Reference를 fetch할 수 없으면(paywall·JS 렌더·dead link) silent pass 하지 않고 **"검증불가"** verdict로 분리 보고한다.
6. **지운 게 있으면 `/validate`로 마감**: 이번 세션에 knowledge 질문·파일을 지웠으면 `/validate`를 돌려 짝 잃은 explained 섹션·파일이 남아 있지 않은지 확인하고 정리한다. 아무것도 안 지웠으면 건너뛴다.
7. **백로그 정리**: ON에서 알린 겹침 목록에 백로그 항목이 있었으면, 이번 세션으로 다 소화된 항목을 지울지 사용자에게 묻는다. 백로그는 별도 레포이므로 KA 커밋과 섞지 않고 따로 커밋한다.
8. [production-guide.md](../../contexts/production-guide.md)의 **스킬 종료 시** 실행 (분할 경고 등)
9. **학습가치 판단 회고**: 이번 세션에 저장 판정이 뒤집힌 적(AI가 「버림」·「해설」로 찍어둔 것을 사용자가 저장으로 바꿨거나, 「저장」으로 찍어둔 것을 버림으로 바꾼 경우)이 있으면 `/pre-exit digest`를 제안한다. 그 번복 유형을 「`제외` 판정 기준」에 반영해 다음 세션 판단을 다듬기 위함이다. 번복이 없었으면 제안하지 않는다.
