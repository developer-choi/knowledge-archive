# Digest

## 목적

공식문서를 읽어 배우고, 그 주제의 [`knowledge/`](../../contexts/directory-roles.md)를 이번 출처 기준으로 다시 쓴다.

## 이번에 읽는 문서가 기준이다

이번에 읽는 문서가 그 주제의 현재 내용이고, KA에 이미 있는 것은 예전에 정리해둔 것이다. 기존 내용과 부딪히면 이번 문서가 이긴다. ON에서 알린 겹침 목록 안의 기존 Q&A는 지워도 된다.

## 공통 규칙

### 세션 중 질문은 질문 로그에 남긴다

ON부터 OFF까지 사용자가 채팅으로 물으면 채팅에 답한 뒤, `os.tmpdir()`의 `ka-digest-<slug>-questions.md`에 `- <대상(문장 head 또는 개념)> | <무엇을 헷갈렸나> | <어떻게 풀어줬나>` 한 줄을 붙인다. OFF 2단계가 이 로그를 explained 재료로 읽는다. 로그는 ON에서 비워 새로 만든다 — 같은 URL의 지난 세션 로그가 섞이지 않게.

### Frontmatter publishable

새로 만드는 knowledge/ 파일의 frontmatter에 `publishable: true`를 박는다.

### 범위 제한
사용자가 제공한 내용의 범위 내에서만 Q&A를 작성한다. 출처 URL을 방문하여 사용자가 언급하지 않은 추가 내용을 가져오지 않는다.

### 기존 미완성 질문 매칭

Q&A를 새로 만들기 전에, 기존 knowledge/ 문서에서 이번 내용과 맞닿는 미완성 질문을 찾는다 — `[UNVERIFIED]` 질문, 그리고 Official Answer 없이 User/Additional Answer만 있는 질문. 마커 정의는 [document-structure.md](../../contexts/document-structure.md)의 "미완성 질문 처리" 참고.

**통째로 다시 쓰기로 한 파일에는 적용하지 않는다** — 그 파일의 빈칸을 채우는 게 아니라 파일 자체를 새로 쓰기 때문이다.

매칭된 질문을 어떻게 채울지는 질문 제안 때 함께 확인받는다.

- **공식 출처 원문이 들어왔다** → Official Answer를 채우고 마커를 제거한다. 기존 Additional Answer는 삭제한다. 기존 User Answer는 새 OA가 그 내용을 다 덮으면 삭제하고, 못 덮는 부분이 있으면 남길지 스스로 판단한다.
- **AI 추정 답변만 가능하다** → Additional Answer로 보강하고 마커는 유지한다.
- **매칭 안 됨** → 새 Q&A를 작성한다. Official Answer가 비어 있으면 `[UNVERIFIED]`를 붙인다.

## 대화형 학습 (ON/OFF)

세션은 **URL 하나당 하나**다.

```
ON [URL] → 루프 — 페이지 순회 → OFF 1단계 — 질문 확정·저장 → OFF 2단계 — 산출물 생성
```

### ON — 모드 시작

[production-guide.md](../../contexts/production-guide.md)의 **Before** 실행.

출처 URL을 기록하고, 질문 로그를 비워 새로 만들고, WebFetch로 해당 페이지의 텍스트 콘텐츠를 가져와 **원본 참조 텍스트**로 보관한다. 이후 단락 검증에 사용한다.

**출처 URL 한글 요약**: 첫 응답에서, 보관한 원본 참조 텍스트를 근거로 페이지 전체의 **한글 요약을 먼저 출력**한다. 요약에는 내용 개요에 더해 아래 축들의 구분을 포함한다:

- **실질적 쓰임새 차이**: 이 페이지를 알면 개발자의 코드 작성 방식이 직접적으로 달라지는 내용
- **몰라도 지장 없는 내부 원리**: 알면 유익하지만 코드 작성법 차이를 직접 유발하지 않는 내부 동작·인프라 수준의 내용

요약이 아래 안내보다 **반드시 먼저** 나간다. 순서: (1) 한글 요약 → (2) 겹치는 것 찾아 알리기 → (3) 안내.

**겹치는 것 찾아 알리기**: 이 주제로 KA에 이미 있는 것을 찾아 요약 뒤에 목록으로 보여준다. 아래 셋을 다 훑어 겹치는 것을 모은다.

- **URL**: 출처 URL이 기존 knowledge/ 문서의 Reference에 이미 있는지
- **주제**: 페이지가 다루는 개념·태그·폴더로 knowledge/를 grep — **URL이 안 걸려도 반드시 한다.**
- **백로그**: 그 주제로 적어둔 백로그 항목 (프롬프트마다 뜨는 백로그 목록에서 고른다)

**손댈 범위는 언제나 겹치는 것 전체다 — 묻지 않는다.** 목록은 "무엇이 갈릴 수 있는지" 알리는 통보이지 승인 요청이 아니므로, 범위를 묻지 말고 곧장 안내로 넘어간다. 사용자가 특정 파일을 빼라고 말하면 그때 그 파일만 뺀다.

겹치는 게 없으면 조용히 넘어가 안내로 진행한다.

여기서 하는 건 **알림뿐이고, 파일을 지우지는 않는다.** 파일마다 어떻게 할지(통째로 다시 쓰기 / 일부만 갈아끼우기 / 그대로 두기)는 페이지를 다 읽은 뒤 OFF 1단계에서 정한다. 아직 안 읽은 뒷부분이 기존 문서 내용을 근거로 쓸 수 있기 때문이다.

URL과 영어 단락이 한꺼번에 와도 요약을 건너뛰지 않는다 — 요약을 먼저 출력한 뒤 그 단락을 「루프 — 페이지 순회」로 넘긴다.

이어서 안내를 출력한다. 담을 것: digest 모드 시작, 단락을 붙여넣으면 문장마다 해설한 화면을 브라우저로 띄운다는 것, 거기서 문장마다 저장·해설·버림을 고르고 복사된 JSON을 붙여넣으라는 것, 페이지를 끝까지 본 뒤 OFF 하면 저장으로 고른 것만 모아 질문을 뽑는다는 것.

### 루프 — 페이지 순회

사용자가 단락을 붙여넣을 때마다 아래를 수행한다. **이 단계에서는 질문을 제안하지 않고, 파일에 저장하지도 않는다.**

#### 0. 원본 페이지 검증

붙여넣은 단락의 핵심 문장이 원본 참조 텍스트에 없으면 해설을 진행하지 않는다. 현재 URL 페이지에 없는 내용이라고 알리고, 다른 페이지의 단락인지 물으며 새 URL을 요청한다. 새 URL을 받으면 WebFetch로 다시 가져와 원본 참조 텍스트를 교체하고, 해당 단락의 해설을 이어서 진행한다.

#### 1. 문장마다 [인용 → 해설] — 브라우저 페이지로 낸다

붙여넣은 단락의 **모든 문장·코드블록**을 문장 하나당 카드 한 장으로 만든다. 여러 단락·문서 전체를 한 번에 붙여넣었어도 그 응답에서 전부 카드로 만든다 — 나눠 학습하고 싶으면 이번 분량을 다 담은 뒤 "다음부터 한 단락씩 붙여넣어 주세요"라고 안내한다.

1. **원문 인용** — verbatim으로 그대로 옮긴다. 이 인용이 OFF 1단계에서 Official Answer의 원본이 되므로 손대지 않는다.
2. **한글 의역** — 원문 의미를 한국어로 푼다. **판정은 라디오가 지고, 이 칸은 어디까지나 의역이다** — 판정 사유로 바꿔치기하지 않는다 (§2).
3. **영단어 해설** — 그 안의 중요 영단어를 `단어: 이 문장에서의 의미` 형식으로 짚는다. 짚을 단어가 없으면 생략한다.
4. **라디오 3택** — 저장 / 해설 / 버림. 기본 선택은 AI 판정으로 미리 찍어둔다 (§2).

2·3은 [CRITICAL] `local/contexts/explanation-guide.md` §1 「본문」의 의역·영단어 해설 양식과 「끊는 기준」, §3 「금지」를 따른다 — 카드를 쓰기 전에 그 파일을 연다. 기억으로 쓰면 여기 옮겨 적히지 않은 금지를 어긴다. 같은 절의 `>` 블록쿼트 인용과 조각 순서는 카드에 적용하지 않는다(원문은 `src`에, 순서는 원문 순서대로).

- 의역이나 영단어 해설을 빼고 라디오만 내보내지 않는다.
- 긴 문장은 「끊는 기준」대로 쪼개 조각마다 의역·단어 해설을 달되, 카드는 문장 하나에 하나이므로 라디오도 하나만 둔다.
- 코드블록·삽화 캡션은 영단어 해설 없이 [인용 → 한 줄 설명 + 라디오]로 처리한다.

무엇이 학습가치가 있고 없는지를 AI가 미리 정해 **해설을 건너뛰지 않는다.** 해설에는 **스킵("넘어간 것") 경로가 없다** — 거르는 일은 라디오가 하고, 해설은 전부 한다.

**깊이는 학습가치에 비례해 조절**한다 (빼는 게 아니라 길이를 줄인다):

- 개념·정의·실무 함의가 있는 문장 → 인용 + 충실한 해설 + 필요한 용어 풀이
- 수사적 도입·전환·군더더기 문장(비유, "다음 섹션 예고" 등) → 건너뛰지 말고 **인용 + 한 줄 의역**으로 처리한다. 역할을 짚고 싶으면 의역 뒤에 한 마디 붙인다 (`하지만 여기에는 또 하나 작용하는 요인이 있다. (다음 논지를 끌어오는 전환 문장)`).

##### 페이지 만들기·열기

카드 내용을 스펙 JSON으로 적어 아래 명령으로 넘긴다 — HTML을 손으로 쓰지 않는다. 열린 절대경로가 돌아오면 채팅에 그대로 적는다.

**스펙 JSON은 레포 안에 만들지 않고 `os.tmpdir()` 아래에 쓴다.** 아래를 한 번에 실행한다. 중간 파일·최종 HTML 모두 임시 폴더에 떨어지므로 뒤처리하지 않는다.

```bash
SPEC="$(node -p 'require("os").tmpdir()')/ka-digest-<slug>-<회차>.json"
cat > "$SPEC" <<'SPEC_JSON'
{ ...스펙... }
SPEC_JSON
npm run --silent build-page -- digest-cards < "$SPEC" \
  | node {{contexts}}/local-html-roundtrip.mjs open ka-digest - --slug <slug>-<회차>
```

스펙은 `{ slug, round, summary, cards: [{ src, ko, words: [{ word, meaning }], verdict }] }`이고, 필드가 위 네 칸과 1:1이다 (`verdict`는 라디오에 미리 찍어둘 AI 판정 — `save`·`explain`·`drop`).

- `<slug>`는 출처 URL의 마지막 경로 조각을 소문자·하이픈으로 바꾼 값 (예: `headings-and-paragraphs`). `<회차>`는 이 세션의 붙여넣기 순번(1부터).
- **`src`에는 원문만 담는다** — 렌더러가 통째로 이스케이프한다. 굵게·코드 표시가 필요하면 `ko`·`words`에서 한다.

##### 채팅에 쓰는 것

원문·의역·영단어 해설·단락 요약을 채팅에 **쓰지 않는다.** 페이지를 열면 채팅에는 문장 수·회차, 열린 HTML의 절대경로, 문장마다 고른 뒤 제출·클립보드 복사를 누르고 복사된 JSON을 붙여넣으라는 안내만 남긴다.

**순회 중 사용자가 채팅으로 물으면 채팅에 답한다** — 위 제한은 페이지 안내에만 걸린다. 답한 뒤 「세션 중 질문은 질문 로그에 남긴다」대로 기록한다.

#### 1-1. 단락 요약

카드가 끝나면 단락 전체의 핵심을 비유와 함께 3줄 이내로 정리해 스펙의 `summary`에 담는다. 판정 건수는 렌더러가 붙이므로 적지 않는다.

#### 1-2. 선택 받기

사용자가 붙여넣은 JSON이 선택 결과다. 클립보드를 뒤지지 않는다. 쓰는 필드는 `items[].head`와 `items[].verdict`(`save`·`explain`·`drop`)다.

- **마커 확인**: `__skill`이 `ka-digest`가 아니면 다른 폼의 값이므로 쓰지 않고 "digest 페이지의 클립보드 복사를 다시 눌러 붙여넣어 주세요"라고 안내한다.
- **회차 확인**: `round`가 이번 회차와 다르면 이전 회차의 잔여이므로 쓰지 않고 "클립보드 복사를 다시 눌러주세요"라고 안내한다.
- 받은 선택은 **원문과 짝지어 세션 안에 쌓아둔다.** `head`로 대조해 순서가 어긋나지 않았는지 확인한다. 이 누적이 OFF 1단계 「후보 취합」의 입력이다.
- 받은 결과는 채팅에 한 줄로만 보고하고 다음 단락을 요청한다. 문장 목록을 다시 나열하지 않는다.

#### 2. 저장 판정

판정은 카드 라디오의 기본값으로 찍는다. 아래 기준은 그 기본값에 적용하고, 최종 결정은 사용자가 화면에서 한다.

##### 「해설」 — knowledge엔 안 가고 explained로 가는 문장

세 판정은 강도가 아니라 **목적지**로 갈린다 — 저장은 `knowledge/`의 Q&A 재료, 해설은 `explained/`의 해설 재료, 버림은 아무 데도 안 남는다. 애매해서 「해설」로 찍지 않는다.

「해설」이 맡는 것은 **그 자체로는 외울 게 없지만 남이 읽을 때 이해를 돕는 문장**이다.

- 앞 문장의 개념을 그대로 풀어 보이는 예시·비유
- 사용자 도메인 안에서 개념의 적용 범위를 넓혀 보여주는 사례 (도메인 밖 사례는 버림 — 아래 「사용자 역할 기준 필터링」)

「버림」으로 남기는 것은 문서 유지보수 배너·목차 링크·계보 귀속처럼 해설에 실어도 독자에게 아무 도움이 안 되는 문장이다.

##### [CRITICAL] 의역 칸은 의역이지 판정 사유가 아니다

의역 칸에는 **판정과 무관하게 그 문장의 한글 의역**을 쓴다. "전환 문장입니다"·"예시입니다"·"수사적 도입입니다" 같은 역할 라벨만 적고 끝내지 않는다 — 역할은 의역 뒤에 덧붙인다. 영문법 구조를 뜯는 서술(explanation-guide §3 「영문법 구조 분석 금지」)도 같다 — 의역을 대신하지 않는다.

##### 사유는 원칙적으로 안 쓴다

사유는 의역만 봐서는 알 수 없는 **해설 밖에서 온 근거**일 때만, 의역 뒤 괄호에 한 문장으로 덧붙인다:

- 기존 knowledge 파일과 중복이거나 거기에 붙일 재료일 때 (파일 경로를 적는다)
- 이 페이지가 아니라 다른 페이지·다음 절에서 다룰 범위일 때
- 앞서 저장 판정한 선행 개념에서 그대로 도출되는 내용일 때

판정에 질문 문장·중요도 라벨·제안 이유를 얹지 않는다 — 그것은 OFF 1단계의 일이다.

##### 중복 검사

판정에 앞서 붙여넣기(단락)마다 한 번, 문장이 아니라 단락 전체를 놓고 수행한다.

- URL 출처가 무매칭이어도 개념·태그·파일명·폴더로 knowledge/를 따로 grep한다 — 같은 내용이 다른 출처 파일에 있을 수 있다.
- knowledge/ 밖 형제 레포 docs(MP `docs/patterns/`·`docs/best-practices/`)도 grep한다 — 테스트·컨벤션·원칙은 MP에 사는 일이 많다.
- 기존 Official Answer와 **완전히 동일한 문장**이면 「버림」
- **같은 개념의 다른 표현**(더 쉬운 설명, 다른 관점, 보충)이면 「저장」으로 찍고 의역 뒤 괄호에 붙일 `knowledge/<경로>.md`를 적는다

단, ON 겹침 목록에 있고 이번 재료가 그 내용을 대체·개정하는 파일과 겹치면 중복이 아니라 갈아끼울 자리라 「저장」으로 찍는다.

##### 버림·해설 판정 기준

knowledge에 안 넣는 기준은 **"알 필요가 없는가"**다 (하드웨어 표준 세부, 관리 체계 등). 쉽다·상식이다·나중에 더 배울 것 같다는 사유가 아니다.

**사용자 역할 기준 필터링**: 사용자의 역할·배경(예: 프론트엔드 개발자, AI 사용자)이 명확하면 그 역할과 무관한 전문 분야 내용은 기본값을 「버림」으로 둔다.
- 비개발 도메인 적용 사례(의료·반도체·물류 등) → 개발자 사용자에게 버림
- 구현·운영 레벨 세부사항(모델 내부 회로, 인프라 설계 등) → 일반 사용자·소비자 역할에게 버림

**상대편이 쓰는 API는 내 코드가 달라질 때만 저장한다**: 사용자의 역할이 한쪽(웹)인데 문서가 양쪽(웹·앱, 프론트·백엔드)을 함께 다루면, 상대편이 부르는 이름 자체는 저장하지 않는다. 가르는 것은 **그것 때문에 내 쪽 코드가 달라지는가**다. 달라지면 저장하되 질문은 내 쪽 결과를 묻는 각도로 세우고, 안 달라지면 해설로 내린다. 바로 위 「사용자 역할 기준 필터링」이 도메인이 아예 다른 경우를 잡는다면, 이 축은 같은 화면을 함께 만드는 상대편을 잡는다.
- **그 API가 왜 생겼는지의 플랫폼 사정**(안드로이드 경합 등)도 같은 축에서 버림이다. 상대편 사정이라 내 코드를 안 가른다.

**이론적 타당 ≠ 실무 빈도**: 1차 소스 근거가 있어도 사용자 역할의 하위 맥락에서 마주칠 빈도가 낮으면 기본값을 「버림」으로 두고, 의역 뒤 괄호에 왜 드문지 메커니즘을 적는다. 단정("잘 안 써요")만 적지 않는다.

**기계적 후속은 「해설」로 찍는다**: 같은 페이지에서 이미 「저장」한 개념에서 기계적으로 유추되는 API 사용 세부(값을 어디서 꺼내는지, 옵션을 어느 인자에 얹는지)는 「해설」로 두어 OFF에서 선행 질문의 해설에 흡수한다. 가르는 질문은 "그 개념을 알면 외울 게 아니라 그때 찾아보면 되는가"다 — 난이도가 아니라 선행 개념에서의 도출 가능성이다.

**계보는 버리고 효용·지침은 저장한다**: 개념의 기원·귀속, 몇 가지 형태로 분류되는지, 어느 책·논문에 실렸는지는 버린다. 그것으로 무엇이 좋아지는지, 무엇을 하라는지, 대가가 무엇인지는 저장한다. 가르는 것은 형식(나열이냐 산문이냐)이 아니라 그 문장이 독자를 판단·행동하게 만드는가다.

**이미지 alt text·캡션은 버림**: 붙여넣은 텍스트에 섞여 들어온 이미지 alt text·캡션(주어-서술어 구조가 없는 나열형 문장)은 Official Answer 재료가 아니다.

### OFF 1단계 — 질문 확정·저장

페이지 순회가 끝나고 사용자가 `OFF`를 입력하면 여기서 시작한다.

#### 후보 취합

회차마다 받아 쌓아둔 선택(「1-2. 선택 받기」)에서 「저장」으로 표시된 문장을 모두 모은다.

「해설」 문장은 어느 질문의 해설에 녹일지 정해 묶어두고, OFF 2단계 explained 생성 에이전트에 넘긴다.

해설 과정에서 도출된 통찰(왜 이런 설계인가, 기존 방식과의 차이, 실무적 의미 등)도 질문 후보로 함께 검토한다. 통찰에 대응하는 영어 원문을 Official Answer로, 통찰 자체는 OFF 2단계에서 생성하는 explained/ 섹션에 보충으로 기록한다. 그 원문이 순회 중 「저장」이 아니었으면 아래 「④ 필터링」의 마지막 줄대로 알리고 확인받는다.

#### 파일마다 어떻게 할지 정하기

ON에서 겹침 목록에 오른 파일마다 아래 셋 중 하나로 정해 확인받는다. 보충 검토·정본 통합보다 먼저 한다.

| 어떻게 | 언제 | 무엇을 하는가 |
|---|---|---|
| 통째로 다시 쓰기 | 문서가 개정돼서 기존 내용 대부분이 지금과 다름 | 파일을 지우고 이번 재료로 새로 쓴다 |
| 일부만 갈아끼우기 | 일부 질문만 낡음 | 낡은 Q&A만 지우고 나머지는 둔다 |
| 그대로 두기 | 이번 문서가 그 부분을 다루지 않음 | 손대지 않는다 |

- **파일 나눔을 이번 문서에 맞춘다.** 기존 파일명·폴더가 이번 문서의 짜임새와 안 맞으면 쪼개거나 합치거나 옮긴다. 기존 배치에 억지로 끼워 넣지 않는다. 옮기거나 이름을 바꿀 때는 `explained/`·`assets/`의 같은 경로도 함께 옮긴다.
- **짝 파일도 같이 지운다**: knowledge 질문·파일을 지우면 `explained/`·`assets/`의 같은 자리도 지운다.
- 범위 밖 파일은 이 절차의 대상이 아니다. 건드릴 일이 생기면 사용자에게 알리고 범위에 넣을지 확인받는다.

#### 기존 답변 보충 검토

「저장」 중 의역 뒤 괄호에 기존 `knowledge/<경로>.md`를 적어둔 재료를 처리한다. 새 질문을 만들기 전에, 그 내용이 기존 Q&A의 답변을 보강할 수 있는지 검토한다.

- **다른 출처의 Official 원문**이 기존 OA와 같은 개념을 다른 표현·각도로 설명하면, 기존 OA에 단락으로 이어 붙이는 보충을 제안한다.
- 기존 답변에 구체적 예시·안티패턴 등 비공식 보충이 필요하면 explained/ 보충을 제안한다. OFF 2단계에서 생성하는 explained/ 섹션에 반영한다.
- 새 질문으로 만들 만큼 독립적이지 않지만, 기존 답변을 풍부하게 만드는 내용이 대상이다.
- **기존 OA에 보충하면 대응 explained도 함께 갱신한다.** 그 explained 섹션이 이미 있으면 OFF 2단계의 갱신 대상에 넣는다.

#### 정본 통합 (SSOT) 판단

**겹침을 찾으면 정본 하나로 몰고 나머지는 참조한다.** 같은 개념이 여러 파일(형제 레포 docs 포함)에 흩어져 있으면 한 곳으로 통합하고 다른 쪽은 그 질문을 참조하게 바꾼다. 신규 저장뿐 아니라 기존 문서를 손볼 때도 적용한다.

- **지우기로 한 파일은 정본 후보에서 뺀다.** 갈아엎기로 한 파일이 있으면 이번에 새로 쓰는 파일이 정본이다.
- **개념 vs 그 구현(API)**이 겹치면 항상 **개념 쪽에 통합**하고 API 쪽은 참조한다.
- 통합할 때 다른 파일에만 있던 측면(정본에 없던 각도·예시)도 함께 흡수한다.
- **참조 형식**: 답변 본문에서는 대상 파일의 해당 질문을 `[상대경로](상대경로)의 「질문 제목」`으로 가리킨다. Questions 목차에서는 [document-structure.md](../../contexts/document-structure.md)의 「꼬리 질문이 다른 md에 있을 때」를 따른다.
- 참조할 건덕지조차 부족하면(정본이 될 쪽이 질문 1개뿐 등) 참조를 남기지 말고 **한쪽으로 완전히 통일**한다.

#### 질문 제안

취합한 재료로 질문을 제안한다.

- **여러 각도로 제안**: 한 개념도 ① 유형의 서로 다른 각도로 낼 수 있다. 유용한 각도는 복수로 내고, 취사는 사용자에게 맡긴다.
  - **단, primary는 담백한 정의·이유형으로.** 복수 각도를 낼 때도 첫 제안(primary)은 개념을 곧이곧대로 묻는 정의/이유 질문으로 하고, 오개념·실무연결 등 영리한 각도는 보조로 붙인다. primary 자리에 오개념 타파나 '다각도 메뉴'를 앞세우지 않는다.
- **각도 2회 반려 시 묻기**: 제안한 질문 각도를 사용자가 2회 이상 반려하면, 새 각도를 추측으로 더 던지지 말고 "어떤 각도·답변을 원하는지" 사용자에게 묻는다.

**① 질문 유형 (메뉴)**
- 일반 질문: "X란 무엇인가?"
- 오개념 타파: "X는 Y를 하는가?" (답이 아니오인 질문)
- 실무 연결: "X가 실제로 해결하는 문제는?"
- 문제→해결: "이런 문제가 있었다. 어떻게 해결하는가?" (recall에 좋다)
- **예시 해석**: 재료에 코드·설정·프로토콜 예시가 있으면 예시를 질문 본문에 그대로 싣고 "각 부분의 역할을 설명하라"로 묻는다.

**② 작성 원칙 (recall 품질)**
- **면접 질문처럼**: 맥락 없이 읽어도 무슨 말인지 이해되어야 한다. 전문 용어로 냅다 시작하지 말고, 상황/배경을 질문 안에 포함한다.
- **개념이 주어면 이름을 대고 묻는다 (수수께끼 금지)**: 질문 대상이 특정 API·개념이면 그 이름을 질문에 그대로 쓰고 곧이곧대로 묻는다. 위 "면접 질문처럼(상황/배경 포함)"은 맥락을 주라는 것이지, 대상 이름을 숨기고 상황만으로 그게 뭔지 맞히게 하라는 게 아니다. 상황 서술은 후보가 여럿이라 가려야 할 때(모호성 제거)만 쓴다.
  - ❌ "각 테스트를 특정 문맥으로 감싼 채 실행해야 할 때 쓰는 훅은?" → ✅ "aroundEach 훅은 무엇을 하며, 어떻게 동작하는가?"
- **정답 키워드 누설 금지**: 사용자가 떠올려야 할 답의 핵심 요소(반환값의 필드명·구성 요소·용어 등)를 질문 문장에 미리 적지 않는다. 막연히 묻고, 그 키워드 산출을 사용자 몫으로 남긴다.
  - ❌ "next()는 무엇을 반환하며 `value`·`done`은 각각 무슨 의미인가?" → 답인 `value`·`done`을 질문이 미리 노출
  - ✅ "next()는 무엇을 반환해야 하며, 그 반환 객체 안의 필드들은 각각 무엇을 의미하는가?" → 사용자가 `value`·`done`을 스스로 떠올려 설명
  - 단, 그 용어 자체가 답이 아니라 질문의 **전제·상황**일 때는 언급해도 된다.
- **리스트 암기 금지**: "3가지는?", "핵심 특성은?", "장단점은?" 식의 나열 질문 금지. 대신 각 항목을 개별 질문으로 분리하거나, 질문에 키워드를 언급하여 이해를 묻는 형태로 만든다.
  - ❌ "BST의 핵심 특성은?" → 사용자가 Ordering Property, Recursive Nature, No Duplicates... 를 줄줄 외워야 함
  - ✅ "BST에서 왼쪽 서브트리와 오른쪽 서브트리의 값은 어떤 관계인가?" → 키워드(ordering property)를 이해하고 설명하는 질문
  - **비교·선택 프레이밍도 리스트 암기일 수 있다**: "A·B·C 중 무엇을 택하나" 같은 비교/결정형이라도, A·B·C가 굳어진 명칭이 아니라 그 문서 안에서만 등장한 임시 분류면 결국 그 목록을 통째로 떠올리라는 리스트 암기다. "담백한 primary"로 위장되지 않으니, 임시 분류는 지우고 단일 개념만 담백하게 묻는다.
- **질문 문장에 코드 호출을 인라인하지 않는다**: `renderHook(...)`처럼 코드를 질문에 그대로 박지 않는다. API를 물으려면 이름을 대고 "~의 시그니처를 설명하라"처럼 묻는다. (예외: ① 유형의 **예시 해석**은 코드를 의도적으로 싣는다.)
- **결론(verdict)을 사실로 암기시키지 말고, 그 결론이 도출되는 원리를 묻는다**: "A가 B보다 낫다/우선한다" 같은 결론 자체를 확인하는 질문 대신, "왜 그런가"를 물어 사용자가 원리로 재구성하게 한다.
  - ❌ "renderHook()보다 render()를 우선시하는가?" → "우선시한다"는 결론만 떠올리면 끝
  - ✅ "재사용 훅을 renderHook 대신 실제 컴포넌트로 렌더해 테스트하면 어떤 차이가 생기는가?" → 우열을 전제하지 않고 원리(실제 사용에 가까움)를 스스로 세우게 함

**③ 배치·위계**
- **정의 먼저**: 재료에 정의·사용법·비교·응용이 함께 있으면 정의 → 사용법 → 비교/응용 순으로 제안한다. 비교·응용·오개념 타파 질문은 같은 주제의 정의 질문을 모두 낸 뒤에만 낸다.
- **정론 먼저, 꼬리질문은 그 다음**: 먼저 개념 자체를 담백하게 묻는 질문(정론)을 만들고, 그 안에서 꼬집을 세부를 꼬리질문으로 붙인다. 오개념 타파 질문을 억지로 만들지 않는다 — 정론이 있어야 꼬리질문이 의미가 있다.
- **위계 구조 일관성**: 사용자가 "톱레벨 + 꼬리질문" 위계를 확립·요구하면 이후 제안도 같은 위계로 구성한다. 질문이 5개 이상 나올 것 같으면 flat 대신 톱레벨 + 꼬리 위계를 기본으로 한다.
- 부모 질문과 꼬리질문의 Official Answer는 내용이 겹쳐도 괜찮다. 단, 완전히 동일한 복붙은 피한다.
- **한 질문에 물음이 둘이면 쪼갠다**: 질문 문장 안에 독립적으로 답할 수 있는 물음이 2개 이상 들어 있으면 각각 별도 질문으로 나눈다("1개로 줄여라"가 아니라 "각각 1개씩으로 나눠라").
  - ❌ "beforeEach·afterEach는 각각 언제 실행되며, 실패해도 afterEach는 도는가?" → ✅ "beforeEach·afterEach는 각각 언제 실행되는가?" / "테스트가 실패해도 afterEach는 실행되는가?"
- **과분할된 중복 질문은 흡수하거나 삭제한다 (억지 흡수 금지)**: 거의 같은 걸 묻는 질문이 여러 개로 쪼개져 답이 대부분 겹치면 한 질문에 흡수한다. 흡수할 실질 내용이 없으면 억지로 합치지 말고 삭제한다. 단, 정당한 부모-꼬리 위계(위 규칙)는 흡수 대상이 아니다 — 위계 없이 같은 층위에서 거의 같은 걸 묻는 형제 질문만 대상이다.
- **페이지 전체를 놓고 배열한다**: 앞부분 문장과 뒷부분 문장이 하나의 답을 이루면 **한 질문으로 합친다** — 등장 순서대로 따로 세우지 않는다.

**④ 필터링**

- **중요도 사전 판단 (내부 전용)**: 질문을 제안할 때, 출처의 성격에 따라 적절한 중요도 기준을 적용하여 **내부적으로** 필터링한다. 중요도 라벨은 사용자에게 **보여주지 않는다**.
  - **라이브러리/프레임워크 공식문서**: "핵심 API" (거의 매번 쓰는 기능), "자주 사용" (알아두면 유용), "고급/니치" (특수 상황에서만 필요) 로 구분한다.
  - **CS 개념/이론 문서**: "면접 핵심", "CS 배경지식", "니치/선택" 으로 구분한다.
  - 출처 URL의 도메인과 경로(예: `/docs/`, API 레퍼런스 등)로 자동 판단한다. 판단이 애매하면 사용자에게 확인한다.
  - 중요도가 섞여 있으면 핵심만 기본 제안하고, 나머지는 선택으로 분리한다.
  - **제안 전 자기 검증**: 각 질문에 대해 아래를 자문한다: (1) "이걸 알면 사용자가 뭘 새로 할 수 있는가?" — 새로운 기능/패턴/가능성이 열리는 내용을 우선 제안한다. (2) "이걸 몰랐을 때 실무에서 어떤 문제가 생기는가?" — 답이 약하면 니치로 분류한다. 니치 항목은 기본 제안에서 제외하고, 사용자가 요청할 때만 제안한다.
- **판단 근거를 먼저 낸다**: 한 페이지에서 질문이 여럿이면, 그 도구·개념을 쓸지 말지·어느 쪽을 고를지 가르는 질문(단점·비용·선택 기준·오개념 교정)을 앞에 세운다. 동작 서술·통과 규칙 같은 설명형은 그 뒤에 붙이고, 자리를 못 얻으면 explained 해설로 보낸다.
- 순회 중 「버림」·「해설」로 정해진 문장은 여기서 질문으로 되살리지 않는다. 되살릴 근거가 생겼으면 그 사실을 사용자에게 알리고 확인받는다.

#### 제안 출력 포맷

질문을 제안할 때 사용자에게 보여주는 것은 **아래가 전부**다:

1. **한글 질문**: 저장될 질문 문장
2. **한글 해설**: 답의 핵심을 한글로 풀어 설명한다(영어 원문 번역 + 요지).
3. **제안 이유**: 이 질문을 왜 제안했는지 한 줄 (recall 가치, 실무 활용, 오개념 교정 등 구체적으로)

**보여주지 않는 것 (내부 처리)**:
- 영어 원문 (Official Answer 후보) — 번역해서 해설로만 노출
- 작업용 내부 라벨·약칭 — [explanation-guide.md](../../contexts/explanation-guide.md) §3 「작업용 내부 라벨·약칭 노출 금지」

사용자가 승인하면 아래 **승인 시 저장** 절차를 실행한다. 거부하면 버린다.

**보류·반려된 질문의 꼬리질문은 함께 보류한다.** 사용자가 톱레벨 질문을 보류·반려하면 그 아래 꼬리질문도 같은 처분으로 묶는다. 사용자가 꼬리질문을 따로 언급하지 않았다는 이유로, 또는 "나머지는 전부 승인" 같은 포괄 승인에 묶인다는 이유로 승인으로 취급하지 않는다. 어느 꼬리가 함께 빠졌는지 보고만 하고 끝낸다 — 살릴지 되묻지 않는다.

#### 승인 시 저장

- [production-guide.md](../../contexts/production-guide.md)의 **After** 전체 실행

**Official Answer는 순회 페이지에 verbatim으로 실어둔 원문을 그대로 옮긴다.** 기억으로 재구성하거나 새로 짓지 않는다. 인용해둔 것과 다른 문장이 필요하면 OA가 아니라 해설이므로 explained로 보낸다.

**지운 게 있으면 커밋을 둘로 나눈다.** 지우기만 담은 커밋을 먼저 쌓고 그 위에 새로 쓴 커밋을 올린다.

짝 파일(`explained/`·`assets/`) 삭제는 knowledge 삭제와 같은 커밋에 넣는다.

저장이 끝나면 사용자 개입 없이 아래 2단계로 이어간다.

---

### OFF 2단계 — 산출물 생성

1. 이번 세션에서 변경한 knowledge 파일 목록과 요약(새 질문 N건, 보충 N건)을 보고한다
2. **priority 확인**: 1의 파일마다(`.sub.md` 제외) frontmatter `priority`를 사용자에게 묻고, 답한 값을 그대로 적는다 — AI는 값을 추측해 채우지 않는다. 질문을 보충한 기존 파일도 대상이며, 값이 이미 있으면 유지할지 함께 묻는다. 값의 뜻은 [content-format.md](../../contexts/content-format.md)의 `priority`.
3. **explained 생성 — 별도 에이전트 위임**: 아래를 넘겨 에이전트가 `explained/<rel>.md`를 쓰게 한다. 에이전트는 이 대화를 못 보므로 넘긴 것만이 재료다.

   **에이전트에 전달할 내용:**
   - 대상 파일 경로: `explained/<rel>.md`
   - 확정된 질문 목록 (OA 원문 포함)
   - 질문별 사용자 오해·막힌 지점·재설명 — 루프의 질문 로그(`os.tmpdir()`의 `ka-digest-<slug>-questions.md`)를 읽어, 세션 맥락 표현 없이 **사실만** 요약
   - 질문 로그 중 확정 질문과 짝이 안 되는 줄은 이 순서로 처리한다: 이번에 손대지 않은 기존 질문을 가리키면 그 explained 섹션에 **덧붙이기만** 할 내용으로 넘기고, 그것도 아니면 가장 가까운 확정 질문의 해설에 붙인다. 어디에도 붙일 곳이 없으면 넘기기 전에 사용자에게 목록으로 알려, 사용자가 고른 질문에 붙이거나 버린다
   - 통째로 교체할 섹션: OFF 1단계에서 OA를 보충한 질문, 다시 쓰거나 갈아끼운 질문
   - 「후보 취합」에서 묶어둔 「해설」 문장(원문 인용·한글 의역)과 통찰 — 각각 어느 질문의 해설에 녹일지 짚어준다
   - 데모·이미지 자산 경로 (있으면) — `assets/<rel>/`에서 explained 본문으로 상대 경로 링크
   - 사용자가 준 공식문서 다이어그램 이미지 URL (있으면) — 에이전트는 이미지를 로컬에 저장하지 않고 WebFetch로 파악해 텍스트 다이어그램(코드블록)으로 옮기고, 섹션 하단에 `원본 다이어그램: [URL]`을 남긴다
   - 적용 규칙: [explanation-guide.md](../../contexts/explanation-guide.md), 섹션 골격은 [document-structure.md](../../contexts/document-structure.md)의 「explained/ 파일 구조」

   **에이전트 지시:** 지정한 섹션만 교체하고, 덧붙이기로 넘긴 내용은 기존 섹션 본문에 녹여 붙이며, 나머지 섹션은 보존한다.
4. **explained 표현 다듬기**: 3에서 쓴 섹션에 `/write-refine`를 돌린다.
   - `>` 블록쿼트로 인용된 영어 원문은 손대지 않는다 ([explanation-guide.md](../../contexts/explanation-guide.md) §1의 원문 인용).
5. **OA 원문 충실도 검증 — 별도 에이전트 위임**: OA를 저장한 메인이 자기 결과를 스스로 채점하지 않도록 독립 에이전트에 맡긴다. 위반은 경고로 보고하고 수정 여부는 사용자가 정한다.

   **대상**: 이번 세션 diff에서 **추가·수정**된 Q&A 중 `source: official`이고 Reference URL이 있는 것. 신규 질문뿐 아니라 기존 OA를 수정·보충한 질문도 포함한다.

   **OA↔Reference 대조**:
   - 각 Q&A의 Reference URL(들)을 WebFetch로 가져와, OA의 각 영어 문장이 원문에 **verbatim substring**으로 존재하는지 대조한다.
   - 매칭은 **문장 단위**다 — 서로 다른 출처·위치의 원문 문장을 그대로 이어 붙이는 것은 허용 정책이므로, 블록·단락 단위로 대조하면 정상 이어붙임이 오검출된다.
   - 어느 Reference 원문에서도 못 찾은 문장은 **"원문 불일치" 경고**로 보고한다 (개작·합성·환각 후보).

   **verdict 규칙 (환각 방지)**:
   - "일치" verdict마다 매칭된 소스 원문 문장을 **인용**한다 — 인용 없는 "verified"는 무효.
   - Reference를 fetch할 수 없으면(paywall·JS 렌더·dead link) silent pass 하지 않고 **"검증불가"** verdict로 분리 보고한다.
6. **지운 게 있으면 `/validate`로 마감**: 이번 세션에 knowledge 질문·파일을 지웠으면 `/validate`를 돌려 짝 잃은 explained 섹션·파일이 남아 있지 않은지 확인하고 정리한다.
7. **백로그 정리**: ON에서 알린 겹침 목록에 백로그 항목이 있었으면, 이번에 다 소화된 항목을 지울지 사용자에게 묻는다(백로그는 별도 레포).
8. [production-guide.md](../../contexts/production-guide.md)의 **스킬 종료 시** 실행
9. **학습가치 판단 회고**: 이번 세션에 AI가 「버림」·「해설」로 찍어둔 카드를 사용자가 저장으로 바꿨거나, 「저장」으로 찍어둔 카드를 버림으로 바꾼 적이 있으면 `/pre-exit`를 제안한다(메뉴의 digest 보강). 번복이 없었으면 제안하지 않는다.
