# Digest — OFF

`OFF` 입력부터 OFF 2단계 끝까지 따른다. 시작할 때 [production-guide.md](../../contexts/production-guide.md)의 **Before**를 실행한다.

## OFF 1단계 — 질문 확정·저장

페이지 순회가 끝나고 사용자가 `OFF`를 입력하면 여기서 시작한다. 아래 번호 순서대로 한다.

### 1. 후보 취합

순회 중 회차마다 받아 쌓아둔 선택에서 「저장」으로 표시된 문장을 모두 모은다.

「해설」 문장은 어느 질문의 해설에 녹일지 정해 묶어두고, OFF 2단계 explained 생성 때 그 질문의 해설에 녹인다.

해설 과정에서 도출된 통찰(왜 이런 설계인가, 기존 방식과의 차이, 실무적 의미 등)도 질문 후보로 함께 검토한다.
통찰에 대응하는 영어 원문을 Official Answer로, 통찰 자체는 OFF 2단계에서 생성하는 explained/ 섹션에 보충으로 기록한다.
그 원문이 순회 중 「저장」이 아니었으면 아래 「④ 필터링」의 마지막 줄대로 알리고 확인받는다.

### 2. 파일마다 어떻게 할지 정하기

ON에서 겹침 목록에 오른 파일마다 아래 셋 중 하나로 정해 확인받는다.

| 어떻게 | 언제 | 무엇을 하는가 |
|---|---|---|
| 통째로 다시 쓰기 | 문서가 개정돼서 기존 내용 대부분이 지금과 다름 | 파일을 지우고 이번 재료로 새로 쓴다 |
| 일부만 갈아끼우기 | 일부 질문만 낡음 | 낡은 Q&A만 지우고 나머지는 둔다 |
| 그대로 두기 | 이번 문서가 그 부분을 다루지 않음 | 손대지 않는다 |

- **파일 나눔을 이번 문서에 맞춘다.** 기존 파일명·폴더가 이번 문서의 짜임새와 안 맞으면 쪼개거나 합치거나 옮긴다. 옮기거나 이름을 바꿀 때는 [directory-roles.md](../../contexts/directory-roles.md) 「원본 이동 시 미러 동반 이동」대로 짝 파일도 옮긴다.
- **짝 파일도 같이 지운다**: knowledge 질문·파일을 지우면 `explained/`·`assets/`의 같은 자리도 지운다.
- 범위 밖 파일은 이 절차의 대상이 아니다. 건드릴 일이 생기면 사용자에게 알리고 범위에 넣을지 확인받는다.

### 3. 정본 판단

**겹침을 찾으면 정본 하나로 몰고 나머지는 참조한다.** 같은 개념이 여러 파일(형제 레포 docs 포함)에 흩어져 있으면 한 곳으로 통합하고 다른 쪽은 그 질문을 참조하게 바꾼다. 신규 저장뿐 아니라 기존 문서를 손볼 때도 적용한다.

- **지우기로 한 파일은 정본 후보에서 뺀다.** 갈아엎기로 한 파일이 있으면 이번에 새로 쓰는 파일이 정본이다.
- **개념 vs 그 구현(API)**이 겹치면 항상 **개념 쪽에 통합**하고 API 쪽은 참조한다.
- 통합할 때 다른 파일에만 있던 측면(정본에 없던 각도·예시)도 함께 흡수한다.
- **참조 형식**: 답변 본문에서는 대상 파일의 해당 질문을 `[상대경로](상대경로)의 「질문 제목」`으로 가리킨다. Questions 목차에서는 [document-structure.md](../../contexts/document-structure.md)의 「꼬리 질문이 다른 md에 있을 때」를 따른다.
- 참조할 건덕지조차 부족하면(정본이 될 쪽이 질문 1개뿐 등) **한쪽으로 완전히 통일**한다.

### 4. 재료를 기존 Q&A에 붙일지 판정

새 질문을 만들기 전에, 재료가 기존 Q&A를 채우거나 보강할 수 있는지 본다. 맞닿는 기존 질문은 두 곳에서 찾는다.

- 「저장」 중 의역 뒤 괄호에 기존 `knowledge/<경로>.md`를 적어둔 재료가 가리키는 질문
- knowledge/ 전체에서 이번 내용과 맞닿는 미완성 질문 — `[UNVERIFIED]` 질문, 그리고 Official Answer 없이 User/Additional Answer만 있는 질문. 마커 정의는 [document-structure.md](../../contexts/document-structure.md)의 "미완성 질문 처리" 참고

| 맞닿은 질문 | 재료 | 처리 |
|---|---|---|
| OA 없음(미완성) | 공식 출처 원문 | OA를 채우고 마커를 제거한다. 기존 Additional Answer는 삭제한다. 기존 User Answer는 새 OA가 그 내용을 다 덮으면 삭제하고, 못 덮는 부분이 있으면 남길지 스스로 판단한다 |
| OA 없음(미완성) | AI 추정 답변뿐 | Additional Answer로 보강하고 마커는 유지한다 |
| OA 있음 | 같은 개념을 다른 표현·각도로 설명한 다른 출처의 공식 원문 | 기존 OA에 단락으로 이어 붙인다 |
| OA 있음 | 구체적 예시·안티패턴 등 비공식 보충 | OFF 2단계 explained 생성 때 그 질문의 explained 섹션에 반영한다 |
| 없음 | — | 5에서 새 Q&A로 제안한다. Official Answer가 비어 있으면 `[UNVERIFIED]`를 붙인다 |

어떻게 채울지는 5의 질문 제안 때 함께 확인받는다.

### 5. 질문 제안

취합한 재료로 질문을 제안한다. 사용자가 제공한 내용의 범위 내에서만 Q&A를 작성한다.

- **여러 각도로 제안**: 한 개념도 ① 유형의 서로 다른 각도로 낼 수 있다. 유용한 각도는 복수로 내고, 취사는 사용자에게 맡긴다.
  - 첫 제안(primary)과 오개념 타파 질문을 붙이는 조건은 [content-format.md](../../contexts/content-format.md)의 「질문 유형 (우선순위)」를 따른다. primary 자리에 '다각도 메뉴'를 앞세우지 않는다.
- **각도 2회 반려 시 묻기**: 제안한 질문 각도를 사용자가 2회 이상 반려하면, 새 각도를 추측으로 더 던지지 말고 "어떤 각도·답변을 원하는지" 사용자에게 묻는다.

**① 질문 유형 (메뉴)** — 일반 질문·오개념 타파 말고 더 낼 수 있는 각도
- 실무 연결: "X가 실제로 해결하는 문제는?"
- 문제→해결: "이런 문제가 있었다. 어떻게 해결하는가?" (recall에 좋다)
- **예시 해석**: 재료에 코드·설정·프로토콜 예시가 있으면 예시를 질문 본문에 그대로 싣고 "각 부분의 역할을 설명하라"로 묻는다.

**② 작성 원칙 (recall 품질)**
- **면접 질문처럼**: 맥락 없이 읽어도 무슨 말인지 이해되어야 한다. 상황/배경을 질문 안에 포함한다.
- **개념이 주어면 이름을 대고 묻는다 (수수께끼 금지)**: 질문 대상이 특정 API·개념이면 그 이름을 질문에 그대로 쓰고 곧이곧대로 묻는다. 위 "면접 질문처럼(상황/배경 포함)"은 맥락을 주라는 것이지, 대상 이름을 숨기고 상황만으로 그게 뭔지 맞히게 하라는 게 아니다. 상황 서술은 후보가 여럿이라 가려야 할 때(모호성 제거)만 쓴다.
  - ❌ "각 테스트를 특정 문맥으로 감싼 채 실행해야 할 때 쓰는 훅은?" → ✅ "aroundEach 훅은 무엇을 하며, 어떻게 동작하는가?"
- **답의 키워드를 질문에 미리 적지 않는다**: 사용자가 떠올려야 할 답의 핵심 요소(반환값의 필드명·구성 요소·용어 등)는 질문 문장에 넣지 않고, 사용자가 스스로 떠올리게 남긴다.
  - ❌ "next()는 무엇을 반환하며 `value`·`done`은 각각 무슨 의미인가?" → 답인 `value`·`done`을 질문이 미리 노출
  - ✅ "next()는 무엇을 반환해야 하며, 그 반환 객체 안의 필드들은 각각 무엇을 의미하는가?" → 사용자가 `value`·`done`을 스스로 떠올려 설명
  - 단, 그 용어 자체가 답이 아니라 질문의 **전제·상황**일 때는 언급해도 된다.
- **리스트 암기 금지**: "3가지는?", "핵심 특성은?", "장단점은?" 식의 나열 질문 금지. 대신 각 항목을 개별 질문으로 분리하거나, 질문에 키워드를 언급하여 이해를 묻는 형태로 만든다.
  - ❌ "BST의 핵심 특성은?" → 사용자가 Ordering Property, Recursive Nature, No Duplicates... 를 줄줄 외워야 함
  - ✅ "BST에서 왼쪽 서브트리와 오른쪽 서브트리의 값은 어떤 관계인가?" → 키워드(ordering property)를 이해하고 설명하는 질문
  - **비교·선택 프레이밍도 리스트 암기일 수 있다**: "A·B·C 중 무엇을 택하나" 같은 비교/결정형이라도, A·B·C가 굳어진 명칭이 아니라 그 문서 안에서만 등장한 임시 분류면 결국 그 목록을 통째로 떠올리라는 리스트 암기다. 첫 제안(일반 질문)인 척해도 리스트 암기이니, 임시 분류는 지우고 단일 개념만 곧이곧대로 묻는다.
- **질문 문장에 코드 호출을 인라인하지 않는다**: `renderHook(...)`처럼 코드를 질문에 그대로 박지 않는다. API를 물으려면 이름을 대고 "~의 시그니처를 설명하라"처럼 묻는다. (예외: ① 유형의 **예시 해석**은 코드를 의도적으로 싣는다.)
- **결론(verdict)을 사실로 암기시키지 말고, 그 결론이 도출되는 원리를 묻는다**: "A가 B보다 낫다/우선한다" 같은 결론 자체를 확인하는 질문 대신, "왜 그런가"를 물어 사용자가 원리로 재구성하게 한다.
  - ❌ "renderHook()보다 render()를 우선시하는가?" → "우선시한다"는 결론만 떠올리면 끝
  - ✅ "재사용 훅을 renderHook 대신 실제 컴포넌트로 렌더해 테스트하면 어떤 차이가 생기는가?" → 우열을 전제하지 않고 원리(실제 사용에 가까움)를 스스로 세우게 함

**③ 배치·위계**
- **정의 → 판단 근거 → 동작 서술 순으로 낸다**: 같은 주제의 정의 질문을 먼저 모두 내고, 그 도구·개념을 쓸지 말지·어느 쪽을 고를지 가르는 질문(단점·비용·선택 기준·비교·오개념 교정)을 그다음에, 사용법·동작 서술·통과 규칙 같은 설명형을 마지막에 붙인다. 설명형이 자리를 못 얻으면 explained 해설로 보낸다.
- **정론 먼저, 꼬리질문은 그 다음**: 먼저 개념 자체를 담백하게 묻는 질문(정론)을 만들고, 그 안에서 꼬집을 세부를 꼬리질문으로 붙인다. 정론이 있어야 꼬리질문이 의미가 있다.
- **위계 구조 일관성**: 사용자가 "톱레벨 + 꼬리질문" 위계를 확립·요구하면 이후 제안도 같은 위계로 구성한다. 질문이 5개 이상 나올 것 같으면 flat 대신 톱레벨 + 꼬리 위계를 기본으로 한다.
- 부모 질문과 꼬리질문의 Official Answer는 내용이 겹쳐도 괜찮다. 단, 완전히 동일한 복붙은 피한다.
- **한 질문에 물음이 둘이면 쪼갠다**: 질문 문장 안에 독립적으로 답할 수 있는 물음이 2개 이상 들어 있으면 각각 별도 질문으로 나눈다("1개로 줄여라"가 아니라 "각각 1개씩으로 나눠라").
  - ❌ "beforeEach·afterEach는 각각 언제 실행되며, 실패해도 afterEach는 도는가?" → ✅ "beforeEach·afterEach는 각각 언제 실행되는가?" / "테스트가 실패해도 afterEach는 실행되는가?"
- **과분할된 중복 질문은 흡수하거나 삭제한다 (억지 흡수 금지)**: 거의 같은 걸 묻는 질문이 여러 개로 쪼개져 답이 대부분 겹치면 한 질문에 흡수한다. 흡수할 실질 내용이 없으면 억지로 합치지 말고 삭제한다. 단, 정당한 부모-꼬리 위계(위 규칙)는 흡수 대상이 아니다 — 위계 없이 같은 층위에서 거의 같은 걸 묻는 형제 질문만 대상이다.
- **페이지 전체를 놓고 배열한다**: 앞부분 문장과 뒷부분 문장이 하나의 답을 이루면 **한 질문으로 합친다**.

**④ 필터링**

- **중요도 사전 판단**: 질문을 제안할 때, 출처의 성격에 따라 적절한 중요도 기준을 적용해 핵심만 기본 제안하고, 나머지는 「선택」 묶음으로 나눠 함께 보여 준다.
  - **라이브러리/프레임워크 공식문서**: "핵심 API" (거의 매번 쓰는 기능), "자주 사용" (알아두면 유용), "고급/니치" (특수 상황에서만 필요) 로 구분한다.
  - **CS 개념/이론 문서**: "면접 핵심", "CS 배경지식", "니치/선택" 으로 구분한다.
  - 출처 URL의 도메인과 경로(예: `/docs/`, API 레퍼런스 등)로 판단한다.
  - **제안 전 자기 검증**: 각 질문에 대해 아래를 자문한다: (1) "이걸 알면 사용자가 뭘 새로 할 수 있는가?" — 새로운 기능/패턴/가능성이 열리는 내용을 우선 제안한다. (2) "이걸 몰랐을 때 실무에서 어떤 문제가 생기는가?" — 답이 약하면 니치로 분류해 「선택」 묶음에 넣는다.
- 순회 중 「버림」·「해설」로 정해진 문장을 질문으로 쓰려면 그 사실을 사용자에게 알리고 확인받는다.

**제안 출력 포맷**

질문을 제안할 때 사용자에게 보여주는 것은 **아래가 전부**다:

1. **한글 질문**: 저장될 질문 문장
2. **한글 해설**: 답의 핵심을 한글로 풀어 설명한다(영어 원문 번역 + 요지).
3. **제안 이유**: 이 질문을 왜 제안했는지 한 줄 (recall 가치, 실무 활용, 오개념 교정 등 구체적으로)

승인을 받을 때 이번에 만들거나 질문을 보충할 파일마다(`.sub.md` 제외) frontmatter `priority`도 묻는다. 값이 이미 있으면 유지할지 함께 묻는다. 값의 뜻은 [content-format.md](../../contexts/content-format.md)의 `priority`.

사용자가 승인하면 6을 실행한다. 거부하면 버린다.

**보류·반려된 질문의 꼬리질문은 함께 보류한다.** 사용자가 톱레벨 질문을 보류·반려하면 그 아래 꼬리질문도 같은 처분으로 묶는다. 사용자가 꼬리질문을 따로 언급하지 않았다는 이유로, 또는 "나머지는 전부 승인" 같은 포괄 승인에 묶인다는 이유로 승인으로 취급하지 않는다. 어느 꼬리가 함께 빠졌는지 보고만 하고 끝낸다.

### 6. 승인 시 저장

- [production-guide.md](../../contexts/production-guide.md)의 **After**를 실행한다. 그중 「Official Answer 원문 대조」는 그 절 대신 아래대로 한다(스크립트로 대조하고, 고칠지는 사용자가 정한다).
  - 「양식 검증」에서 나오는 「대응 explained 없음」 위반은 2단계 explained 생성이 채우므로 여기서 고치지 않는다.
- 새로 만드는 knowledge/ 파일의 frontmatter에 `publishable: true`를 박는다.
- 5에서 `priority`를 물은 파일마다(질문을 보충한 기존 파일 포함) 답한 값 그대로 적는다.

**Official Answer는 순회 페이지에 verbatim으로 실어둔 원문을 그대로 옮긴다.** 인용해둔 것과 다른 문장이 필요하면 OA가 아니라 해설이므로 explained로 보낸다.

**저장한 OA를 Reference 원문과 대조한다.** 대상은 이번 세션에 OA를 추가·수정한 Q&A 전부다(파일의 `source` 값과 상관없다).
- Reference URL마다 `npm run --silent digest -- page <URL>`로 원문을 받고, OA를 `npm run --silent digest -- has <URL> --md`에 heredoc stdin으로 넘긴다.
- 받은 어느 원문에서도 X인 문장은 「원문 불일치」로 경고 보고한다. 그 Q&A에 `page`가 실패한 Reference가 있으면 「원문 불일치」 대신 「검증불가」로 보고한다. 고칠지는 사용자가 정하고, 정한 대로 고친다.

저장이 끝나면 커밋하지 않고 사용자 개입 없이 아래 2단계로 이어간다. 커밋은 explained까지 쓴 뒤 2단계 「검사·커밋」에서 한다 — 린터가 knowledge와 대응 explained를 짝으로 보기 때문이다.

## OFF 2단계 — 산출물 생성

1. 이번 세션에서 변경한 knowledge 파일 목록과 요약(새 질문 N건, 보충 N건)을 보고한다
2. **explained 생성**: 메인이 `explained/<rel>.md`를 쓴다.

   **재료:**
   - 확정된 질문 목록 (OA 원문 포함)
   - 질문별 사용자 오해·막힌 지점·재설명 — `npm run --silent digest -- read <slug>`로 질문 로그를 읽어, 세션 맥락 표현 없이 **사실만** 반영
   - 질문 로그 중 확정 질문과 짝이 안 되는 줄은 이 순서로 처리한다: 이번에 손대지 않은 기존 질문을 가리키면 그 explained 섹션에 **덧붙이기만** 하고, 그것도 아니면 가장 가까운 확정 질문의 해설에 붙인다. 어디에도 붙일 곳이 없으면 쓰기 전에 사용자에게 목록으로 알려, 사용자가 고른 질문에 붙이거나 버린다
   - 통째로 교체할 섹션: OFF 1단계에서 OA를 채우거나 보충한 질문, 다시 쓰거나 갈아끼운 질문
   - 1단계 「1. 후보 취합」에서 묶어둔 「해설」 문장(원문 인용·한글 의역)과 통찰
   - 1단계 「4. 재료를 기존 Q&A에 붙일지 판정」에서 explained로 보낸 비공식 보충
   - 데모·이미지 자산 경로 (있으면) — `assets/<rel>/`에서 explained 본문으로 상대 경로 링크
   - 사용자가 준 공식문서 다이어그램 이미지 URL (있으면) — `npm run --silent digest -- image <URL>`이 tmp에 받은 파일을 Read로 열어 텍스트 다이어그램(코드블록)으로 옮기고, 섹션 하단에 `원본 다이어그램: [URL]`을 남긴다
   - 적용 규칙: [explanation-guide.md](../../contexts/explanation-guide.md), 섹션 골격은 [document-structure.md](../../contexts/document-structure.md)의 「explained/ 파일 구조」

   **쓰는 법:** 교체할 섹션만 교체하고, 덧붙이기로 한 내용은 기존 섹션 본문에 녹여 붙이며(`## 오해 교정` 같은 별도 섹션을 만들지 않는다), 나머지 섹션은 보존한다. 출처·작성 시점은 경로·H1·git 이력으로 알 수 있으니 frontmatter 등 메타데이터를 박지 않는다.
3. **explained 표현 검사**: 2에서 쓴 파일에 아래 둘을 돌려, 걸린 줄 중 2에서 쓰거나 교체한 섹션 안의 줄만 고친다.
   - `node ~/.claude/skills/write-doc/scripts/score.mjs <파일>`
   - `node ~/.ai-contexts/check-wording.mjs --report <파일>`
   - score.mjs의 「습니다체 휴리스틱」 항목은 고치지 않는다. explained는 「~다」체로 쓴다.
   - `>` 블록쿼트로 인용된 영어 원문은 손대지 않는다 ([explanation-guide.md](../../contexts/explanation-guide.md) 「본문」의 원문 인용).
4. **검사·커밋**: 커밋 전에 `npm run validate-lint -- <이번에 쓴 knowledge·explained 파일>`을 돌려 나온 위반을 고친 뒤, knowledge와 explained를 함께 커밋한다. 지운 게 있으면 아래를 더한다.
   - 커밋 전에 `/validate`를 돌려 짝 잃은 explained 섹션·파일이 남아 있지 않은지 확인하고 정리한다.
   - 커밋을 둘로 나눈다. knowledge 삭제와 짝 파일(`explained/`·`assets/`) 삭제만 담은 커밋을 먼저 쌓고, 그 위에 새로 쓴 커밋을 올린다.
5. **백로그 정리**: ON에서 알린 겹침 목록에 백로그 항목이 있었으면, 이번에 다 소화된 항목을 지울지 사용자에게 묻는다(백로그는 별도 레포).
6. [production-guide.md](../../contexts/production-guide.md)의 **스킬 종료 시** 실행
7. **학습가치 판단 회고**: 이번 세션에 AI가 「버림」·「해설」로 찍어둔 카드를 사용자가 저장으로 바꿨거나, 「저장」으로 찍어둔 카드를 버림으로 바꾼 적이 있으면 `/pre-exit`를 제안한다(메뉴의 digest 보강).
