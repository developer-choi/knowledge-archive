# 내용 작성 규칙

문서의 각 섹션을 작성할 때 지켜야 하는 형식 및 내용 규칙입니다.

---

## 0. 기본 원칙

- **Fact-First**: 객관적 사실만 Official Answer에 기록. 해석·보충은 Additional Answer 또는 User Answer로 분리한다.
- **원문 보존**: 공식 문서 원문은 문장 간 연결이 어색해도 AI가 가공하지 않는다. 통합·재배치·마이그 중에도 원문을 잃지 않는다(형태는 바뀌어도 된다). 출처가 개정돼 현행이 아닌 원문은 지워도 된다 — git 이력에 남는다.
- **언어**: Official Answer 밖의 편집 섹션(Questions, Additional Answer, Review Note, Frequent Mistakes 등)은 한글로 쓴다.
- **출처 없으면 작업 중단**: 출처가 제공되지 않으면, 내용 작성 전에 출처 링크를 요청하고 대기한다.
- **비속어 금지**: 문서 어디에도 욕설·비속어를 쓰지 않는다. 강조는 일반 어휘로 한다.

## 1. Frontmatter

### tags

#### 작성 규칙
- [공식 태그 목록](tags.md)에서 선택
- 우선순위: 기술명 > 카테고리 > 특성

#### 새 태그 추가
- 공식 태그 목록에 맞는 태그가 없으면 그 목록에 먼저 추가를 제안한다

---

### source

**파일이 어떤 맥락에서 만들어졌는가**를 나타낸다. Q&A 개별 출처 신뢰도가 아님 — 개별 신뢰도는 `[UNVERIFIED]` 마커와 `### Reference`가 담당한다.

| 값 | 의미 |
|----|------|
| `official` | MDN·Wikipedia 등 1차 소스를 직접 읽으면서 작성 |
| `google-doc` | 구글 문서 등 외부 필기에서 변환된 파일 |
| `unverified` | 출처 미추적 (유튜브·교재·개인 메모 등 기반) |

- 파일을 나눌 때는 원본의 `source` 값을 모든 파생 파일에 그대로 물려준다.

---

### priority

knowledge/ 문서의 면접 대비 우선순위.

| 값 | 의미 |
|----|------|
| `1` | 기술면접 필수 대비 — 어떤 기술면접이든 준비하는 기저 항목 |
| `2` | 공고에서 해당 주제를 추가로 요구·언급할 때만 깊게 준비하는 항목. 언급이 없으면 아주 흔한 기본만 준비한다 |
| `5` | 참고용 (나중에 찾아볼 수도 있어서 보관) |
| (키 없음·빈 값) | 미분류 |

- **AI는 priority를 추측해 채우지 않는다** — 사용자가 학습 전략에 따라 정하는 값이다. 사용자가 정해 준 값은 AI가 대신 적어도 된다.
- 빈 키(`priority:`)를 새로 심지 않는다. 키는 값이 정해질 때 함께 넣는다.

## 2. Questions 섹션

### 질문 생성
질문이 명시되지 않았다면, **면접 질문 형태**로 생성합니다.

#### 절대 원칙
- 질문은 **답변 섹션(Official Answer, Additional Answer, User Answer)의 내용으로 답할 수 있어야** 한다.

#### 답변 분할
- 하나의 Official Answer가 여러 독립된 내용을 포함하면, 내용 덩어리별로 질문을 분리한다.
- 하나의 어색한 질문보다 여러 개의 자연스러운 질문이 낫다.

#### 질문 유형 (우선순위)
1. **일반 질문**: 개념을 곧이곧대로 묻는 정의·이유 질문을 먼저 세운다.
2. **오개념 타파(Trick Questions)**: Official Answer가 흔한 오해를 반박하는 내용을 포함할 때만 보조로 붙인다.

## 3. Answer 섹션

세 가지 Answer 유형이 있다.

| 섹션 | 출처 | 용도 |
|---|---|---|
| `### Official Answer` | 공식 문서 | 검증된 사실. 확보 가능하면 포함 |
| `### Additional Answer` | 공식 문서 아님 (AI·사용자 작성) | 공식 출처 미확보 or OA에 없는 보충 — 면접 답변 수준 암기 필요 |
| `### User Answer` | 사용자 작성 | 사용자의 해석, 경험 기반 답변 |

### 작성 원칙
- **빈 섹션 금지**: 채울 본문이 없는 섹션 헤딩(`### Official Answer`, `### Additional Answer`, `### User Answer`, `### Reference`, 그리고 아래 §5의 `### Review Note`·`### Frequent Mistakes`)은 만들지 않는다. 본문이 생기는 시점에 섹션을 추가한다.
- **OA 단락 통합**: 같거나 다른 공식 출처의 원문 단락 여러 개를 빈 줄로 나눠 한 Official Answer에 이어 붙여도 된다.
- **출처 표기는 Reference에만**: OA 본문에 인라인 출처를 두지 않고, 모든 출처 URL은 `### Reference`에 모은다.
- **OA 내부 위계화**: OA가 단락 여럿으로 길거나 카테고리로 묶이면(예: "정의 / 구성요소 / 동작 방식") `####` H4로 나눈다.
- **OA 길이 관리**: OA가 길면 긴 단락은 쪼개고, 단락이 많으면 질문을 나눠 옮긴다.
- **OA 한글 금지**: OA에 한글이 0이어야 "원문인가 내가 쓴 것인가"를 사람이 매번 판단하지 않고 린터가 가린다. `####` 소제목은 구조 표시라 예외다.
  - 같은 이유로 영어 보충(대괄호로 끼워 넣기 등)도 넣지 않는다 — 원문에도 대괄호가 쓰여 보충분과 구분이 안 된다.
- **원본 언어 유지 (번역 금지)**: User Answer가 한글이면 한글 그대로 작성한다.
  - 허용 편집: 맞춤법, 조사, 문장 흐름, 전문 용어 정확화
  - 금지: 소스에 없는 새 사실 덧붙이기, 뉘앙스 변경, 근거 없는 주장
- **명백한 사실 오류 정정**: 위키피디아 수준의 확립된 지식(표준 수치·프로토콜 헤더 필드·레지스터 정의 등)과 충돌하거나 같은 섹션 안에서 자기모순이 있으면 User Answer·Additional Answer에서 정정한다.
- **출처 명확성**: Official Answer의 출처는 Reference에 적는다.
- **출처-Answer 매핑**: Reference에 공식 출처 URL이 있고 Official Answer가 아직 없는 상태(학습 진행 중)는 위반이 아니다.
- **동일 헤딩 중복 금지**: 한 Q&A 안에서 같은 섹션 헤딩은 하나만 두고, 겹치면 내용을 합친다.

## 4. Reference

### 작성 규칙
- 공식 문서 URL 또는 위키피디아 링크 제공
- 링크 형식: 순수 URL만 기재 (Markdown 링크 문법 사용 X)
- 출처는 아는데 URL을 모르면 `- 출처 설명 (URL_UNKNOWN)`

---

## 5. Review Note / Frequent Mistakes

Q&A 블록 안에 H3로 추가할 수 있는 선택적 섹션이다.

| 섹션 | 용도 |
|---|---|
| `### Review Note` | 복습·평가 시 참고사항 (중요하지 않은 부분, 집중할 부분 등) |
| `### Frequent Mistakes` | 복습 시 자주 혼동한 키워드나 오개념 기록 |

- **Answer 내 위치**: Reference 바로 위에 배치한다.

## 6. 이미지 처리

### Case 1: 다른 AI 답변 캡처
다른 AI 답변 이미지를 옮길 때는 내용의 성격에 따라 처리한다:
- 면접 답변 수준 암기가 필요한 내용 → `### Additional Answer`로 추가
- 보조 컨텍스트 수준 → 옮기지 않는다

### Case 2: 공식 문서 캡처 (다이어그램, 표)
- 이미지가 핵심 정보를 담고 있으면 텍스트로 변환

### Case 3: 외부 이미지
- 가능하면 텍스트 설명으로 대체
- 원본 이미지 출처를 Reference에 명시
