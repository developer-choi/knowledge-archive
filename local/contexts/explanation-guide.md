## 0. known→unknown 원칙 (모든 설명에 선행 적용)

좋은 설명의 유일한 조건: 학습자가 어렴풋이라도 아는 것에서 출발해, 아직 모르는 것에 도달하게 한다. 모르는 단어로 설명하면 못 알아듣고, 아는 것을 또 정의하면 지루하다.

### 발판 높이 보정 (설명 생성 전 1회)

1. 베이스라인: JS·HTML·CSS·브라우저·Node.js 생태계 개념은 정의 없이 발판으로 쓴다.
2. `explained/` 트리 조회로 베이스라인을 보정한다:
   - 폴더·파일명을 훑어 학습자가 어느 영역을 공부했는지 대략 파악한다(예: `cs/network/` 아래 파일이 많으면 네트워크 기초는 깔려 있다).
   - 설명할 개념과 관련된 explained 파일을 열어 H1 헤딩(질문 제목)만 읽는다. 어떤 개념이 헤딩으로 다뤄졌으면, 그 개념은 학습자가 한 번 이상 설명을 받은(=어렴풋이 아는) 것이므로 발판으로 쓴다.
   - **발판으로 인용하는 헤딩은 파일에서 실제로 읽어 확인한 H1 원문 그대로 쓴다.** "파일이 있으니 그 개념도 다뤘겠지" 식으로 존재하지 않는 헤딩을 만들어내지 않는다. 파일은 있으나 해당 개념의 H1이 없으면 그건 발판이 아니다 — 미학습 용어로 취급한다.
   - 발판이 다루는 **세부 측면**(예: "HTTP가 TCP 위에서 동작")을 헤딩 자리에 적지 않는다. 인용은 H1 제목 원문(예: "HTTP란 무엇인가?")이고, 그 측면은 설명 본문에서 풀어 쓴다. 제목을 측면으로 바꿔 적으면 실제 H1과 어긋난다.

### 설명 중 행동 규칙

- 발판 = 베이스라인 + explained 헤딩에 있는 개념. 이 둘은 정의 없이 비유·선행지식으로 바로 쓴다.
- **발판으로 확인된 개념은 재정의하지 않는다.** "X란 ~이다"로 다시 풀지 말고, 이미 아는 것으로 전제하고 새 개념을 그 위에 얹는다.
- 베이스라인도 아니고 explained 헤딩에도 없는 용어는, 첫 등장하는 그 자리에서 한 줄로 정의한 뒤 쓴다. 미뤄 던지지 않는다.
- 같은 뜻을 발판 용어로 풀 수 있으면, 미학습 용어를 애초에 꺼내지 않는다.

## 1. 포맷 — 영어 원문 해설의 3단계 흐름

영어 공식문서 원문을 한글로 해설할 때 사용하는 구조. 원문(Official Answer)이 항목 목록이면 도입·본문·종합 모두 그 구조를 유지한다. 항목을 산문으로 녹여 없애면 무엇이 몇 개였는지가 사라진다.

### 도입

- 둘 중 하나(또는 둘 다)를 제공한다:
  - **사전 배경지식**: 원문을 이해하기 위해 먼저 알아야 할 개념·용어·맥락.
  - **해설 요약본**: 원문이 전달하는 핵심 주장의 한글 요약.
- 뒤이어 나올 질문의 정답을 미리 알려주지 않는다.

### 본문

각 조각마다:

1. 원문 조각을 `>` 블록쿼트로 인용한다.
2. **한글 의역을 한 줄로 적는다.**
3. 그 안의 중요 영단어를 `- **단어**: 이 문장에서의 의미` 형식으로 해설한다.
   직역만으로 의미가 모호하거나 단어 선택의 의도가 중요한 단어를 우선해, 정의를 외우게 하지 말고 왜 그 단어가 쓰였는지 짚는다.

**끊는 기준**

- 기본은 콤마·and·접속사 단위.
- 단위가 너무 짧거나 해설할 단어가 없으면 다음 단위까지 묶는다.
- 한 문장이 짧고 명확하면 굳이 쪼개지 않는다.

**조각 순서**

끊은 조각을 원문에 적힌 차례대로 늘어놓지 않는다. 순서는 해설자가 정한다.

기준은 하나다. **그 질문의 답이 서는 데 필요한 조각이 앞에 온다.** "A란 무엇인가?" 류라면 A의 정의 조각이 앞이고, 왜 필요한지·어떻게 동작하는지는 그 뒤다. 정의가 맨 앞에 오는 것은 이 기준을 그 질문에 적용한 결과이지 기준 자체가 아니다 — 질문이 달라지면 앞에 오는 조각도 달라진다.

옮기는 단위와 한계:

- **옮길 수 있는 단위는 조각(문장)이다.** 문장 안에서 단어를 재배열하거나 두 문장을 잘라 섞지 않는다.
- **앞 조각에 매달린 조각은 함께 옮긴다.** `In other words` · `Then` · `this` · `these` · `such`처럼 바로 앞 문장을 전제하는 말이 들어 있으면 그 묶음이 한 덩어리다. 떼어서 앞으로 보내면 가리키는 대상이 사라진다.
- **앞에 온 조각이 아직 모르는 말을 품고 있으면 그 발판은 「도입」으로 내린다.** 발판을 본문 앞에 소주제로 끼워 순서를 되돌리지 않는다 (§0 known→unknown).

**옮긴 뒤에 남는 일** — 조각을 옮기면 그 조각을 가리키던 한글 해설이 같이 어긋난다. 재배열은 조각을 옮기는 데서 끝나지 않고, 옮긴 조각을 지목하던 문장을 훑어 고치는 데까지다.

- **방향이 뒤집힌 지목**: "앞 절에서 본 ~", "앞의 세 문장이 ~"처럼 위치로 가리키던 말이 이제 뒤를 가리키게 됐으면 고쳐 쓴다.
- **끊어진 흐름을 잇는 한 줄**: 원문 순서가 만들어주던 이유→귀결의 연결이 새 순서에서 끊기면, 그 자리를 여는 문장을 새로 쓴다.

### 종합

- 끊은 조각들이 어떻게 하나의 전체를 이루는지 엮는다.
- 개별 단어 해설의 반복이 아니라, 원문 전체의 뼈대·흐름·의의를 다시 조립한다.
- "왜 이렇게 동작하는가", 실무에서 어디서 마주치는가 같은 의역적 맥락을 여기서 통합한다.

## 2. 예시와 비유

### 예시와 비유를 구분한다

- **예시**: 해당 개념의 실제 인스턴스. OS 문서라면 OS 레벨의 실제 동작이나 시스템 콜이 예시다.
  - 맞음: "I/O 대기 예시: `read()` 시스템 콜 블로킹"
  - 맞음: "자발적 양보 예시: `sched_yield()` 시스템 콜"
- **비유**: 개념을 이해시키기 위해 다른 도메인에서 빌려온 것. JS 코드로 OS 개념을 설명하면 그것은 비유다.
  - 맞음: "**JS 비유:** `fs.readFile()` 대기가 OS I/O 블로킹과 비슷한 구조"
  - 틀림: 테이블 "예시" 컬럼에 `fs.readFile()`을 넣는 것 (예시처럼 보이지만 실제론 비유)
- 비유는 §0 베이스라인(JS/브라우저/Node.js)에서 가져온다. 학습자가 매일 보는 실제 인스턴스(Chrome 탭이 별도 프로세스로 뜨고 IPC로 통신, Task Manager의 프로세스 목록·PID)는 비유가 아니라 예시로 쓴다.
- JS 코드·API로 다른 도메인의 개념을 빗댄 것은 그 자리에 `**JS 비유:**` 레이블을 붙여 예시와 구분한다.

### 코드로 표현 가능한 개념은 코드 예시로 보여준다

설명을 문장으로만 나열하지 말고, 코드로 표현할 수 있는 개념이면 **쉬운 코드 예시**를 함께 넣는다. 실행 흐름·실패 지점·계층 차이는 문장 열 줄보다 코드 몇 줄이 훨씬 빨리 이해된다. 실생활 비유보다 실제 코드 실행을 먼저 고른다.

작성 규칙:

- **지어낸 도메인 헬퍼 금지**: `writeAndSave()`·`addToCart()`처럼 "이 함수 뭐야?"를 유발하는 가짜 함수를 만들지 않는다. 누가 봐도 자명한 시나리오(로그인 등)를 고른다.
- **핵심 아닌 셋업은 삭제하거나 주석 한 줄로 대체**: 예 `// 로그인 + 장바구니에 상품 담긴 상태로 시작`. 문제가 되는 코드 한 줄 위에 긴 셋업을 쌓지 않는다.
- **딱 설명할 만큼만**: 예시의 목적은 한 지점을 스포트라이트하는 것이다. 핵심 라인은 `// ← 여기서 실패`처럼 주석으로 짚어 시선을 모은다.
- **레벨을 정확히**: 그 맥락에서 실제로 쓰는 API·계층을 지킨다. 예로 E2E 테스트는 브라우저 UI를 구동하지 앱 내부 훅(`mutateAsync`·axios 등)을 직접 부르지 않는다 — 그건 유닛/프로덕션 코드 레벨이다.
- **줄이되 왜곡하지 않는다**: 위 「핵심 아닌 셋업은 삭제」·「딱 설명할 만큼만」과 「지어낸 도메인 헬퍼 금지」 사이의 경계. 군더더기는 빼되 실제 코드의 뼈대(비동기·실패·호출 구조)는 남긴다. 억지 단순화로 현실과 괴리되면 오히려 "이게 진짜 코드야?" 의심을 부른다.

### 설명에 함께 넣을 것

- 개념이나 값을 설명할 때 그것이 없으면 어떤 문제가 생기는지를 함께 제시한다. "무엇인가"만 설명하면 추상적으로 느껴지지만, "없으면 어떻게 되는가"를 붙이면 존재 이유가 구체화된다.
- 항목이 여럿 나열되는 내용을 줄글 한 문단에 뭉치지 않는다. 항목마다 한 줄씩 불릿으로 편다.

## 3. 금지

- **영문법 구조 분석 금지**: "이 문장은 A comprises B, C, D 구조다" 같은 구조 분석은 도입·본문·종합 어디에도 넣지 않는다.
- **발판 보정 과정·캐시 여부 노출 금지**: "이건 이미 설명한 내용이라", "캐시에 있어서" 같은 메타 멘트는 학습자에게 가치가 없다. 보정은 내부에서만 하고, 본문은 곧장 설명으로 들어간다.
- **신조어·불명확한 비유 금지**: 사전에 없거나 뜻이 바로 안 잡히는, AI가 즉석에서 만들어낸 압축 표현·비유로 설명하지 않는다.
  일상어로 먼저 전달하고, 비유가 꼭 필요하면 그 자리에서 풀어 쓴다. 이미 나온 즉석 표현은 explained를 쓸 때 digest off.md 「explained 표현 검사」의 check-wording이 잡는다.
- **작업용 내부 라벨·약칭 노출 금지**: 제안·검토 과정에서 쓰는 임시 기호(`Q1`/`Q2`, `(A)`/`(B)`, `primary`, 코드 실행용 임시 이름 `runSuite` 등)를 설명·대화에 그대로 내보내지 않는다. 학습자에겐 뜻 없는 내부 기호이므로, 가리키려는 대상을 풀어 쓴다.
  - ❌ "`Q1`의 (A) 케이스를 primary로 저장할까요?"
  - ✅ "첫 번째 질문의 '재사용 훅' 경우를 기본 질문으로 저장할까요?"
- **AI 추론을 공식 권장·확립된 사실로 단정 금지**: 공식 문서에 없는 판단·기준을 "공식 권장", "~라고 한다"처럼 출처가 있는 양 서술하지 않는다. 공식 여부가 중요하면 1차 소스를 직접 확인해 인용하고, 확인 못 했으면 추정임을 명시한다.
- **세션 맥락 표현 금지**: 아래 「세션 맥락 표현 목록」의 문구를 쓰지 않는다.
  - 세션에서 나온 오해·재설명의 **내용**은 포함하되, **독자 관점의 보편적 표현**으로 재구성한다.
  - ✅ "흔히 혼동하는 지점이다", "헷갈리기 쉬운 부분이다", "주의할 점이 있다"

### 세션 맥락 표현 목록

린터가 아래 목록을 읽어 `explained/`를 검사한다 (위반은 `E9`로 출력된다). 목록이 곧 규칙이라 사람이 고치는 자리와 기계가 읽는 자리가 하나다. 새 표현이 나오면 여기에 한 줄 추가한다.

낱말이 아니라 **문구**로 잡는다. "세션"만 보면 HTTP 세션 설명이 걸린다.

## 4. 다이어그램

설명 중 아래 트리거에 걸리는 부분이 나오면 다이어그램을 함께 작성한다. 위치는 본문(해당 조각 옆) 또는 종합(전체 시각화) 자율. 한 질문에 여러 트리거가 걸리면 다이어그램도 여러 개 — 개수는 가변이다.

### 트리거 4종

| 트리거 | 언제 | 형식 |
|---|---|---|
| **구조(Structure)** | "구성된다", "포함", "계층" — 요소 2개 이상 | 트리 / 네스티드 박스 |
| **흐름(Flow)** | "→", "이후", "단계", 상태 전이 | 화살표 / 상태도 |
| **공간(Layout)** | 메모리 영역, 레지스터, 디스크 블록 | 박스 레이아웃 |
| **비교(Compare)** | "vs", "차이", "반면" — 2개 이상 대상 | side-by-side 매트릭스 |

### 예시 (구조 트리거)

```
프로세스
├── program code ──────────────────────→ 텍스트 영역
├── system resources
│   └── memory
│       ├── 텍스트 영역   실행 기계어
│       ├── 데이터 영역   전역변수
│       ├── 스택          지역변수·매개변수
```
