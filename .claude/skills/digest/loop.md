# Digest: ON·루프

`ON [URL]`부터 `OFF` 입력 전까지 따른다.

## ON: 모드 시작

1. **준비**: 출처 URL을 기록하고, SKILL.md [slug는 ON의 URL로 정해 끝까지 쓴다](SKILL.md#slug는-on의-url로-정해-끝까지-쓴다)대로 slug를 얻어 `npm run --silent digest -- reset <slug>`로 질문 로그와 회차 기록을 비운다.
   `npm run --silent digest -- page <URL>`로 페이지 원문을 받아 둔다. 한글 요약과 0단계 대조가 이 원문을 사용한다.
   `page`가 실패하면 stderr를 사용자에게 보이고 멈춘다. 원문 없이는 0단계 대조를 할 수 없다.
2. **한글 요약**: 받아 둔 원문을 읽고 페이지 전체의 한글 요약을 출력한다. 내용 개요를 적고, 아래 축으로도 나눈다.
   - **실질적 쓰임새 차이**: 이 페이지를 알면 개발자의 코드 작성 방식이 직접적으로 달라지는 내용
   - **몰라도 지장 없는 내부 원리**: 알면 유익하지만 코드 작성법 차이를 직접 유발하지 않는 내부 동작·인프라 수준의 내용
3. **겹치는 것 알리기**: 이 주제로 KA에 이미 있는 것을 요약 뒤에 목록으로 보여 준다. 아래를 모두 훑는다.
   **URL**·**백로그**는 메인이 직접 찾고, **주제**는 Explore 서브에이전트(`model: sonnet`)에 페이지에 나오는 개념·태그를 넘겨 맡겨 겹치는 파일 경로와 질문 제목만 돌려받는다.
   경로와 제목을 모으는 일이라 sonnet으로 낮추고, 파일 일부를 읽어 겹치는지 알아내야 해서 haiku까지는 낮추지 않는다.
   - **URL**: `npm run --silent digest -- refs <URL>`이 출력하는, 출처 URL이 걸린 knowledge 파일
   - **주제**: 페이지에 나오는 개념·태그와 그에 맞는 폴더로 knowledge/를 검색한다. URL이 안 걸려도 한다.
   - **백로그**: `~/WebstormProjects/main/backlog/projects/knowledge-archive/` 아래(dev-active·dev-inactive)에서 그 주제 항목

   **손댈 범위는 언제나 겹치는 것 전체다.** 묻지 않고 곧장 안내로 넘어간다.
   파일마다 어떻게 할지는 페이지를 다 읽은 뒤 OFF에서 질문을 확정할 때 정한다. 아직 안 읽은 뒷부분이 기존 문서 내용을 근거로 삼을 수 있기 때문이다.
4. **안내**: 담을 것은 아래다.
   - digest 모드 시작
   - 단락을 붙여넣으면 문장마다 해설한 화면을 브라우저로 띄운다는 것
   - 거기서 문장마다 저장·해설·버림을 선택하고 복사된 JSON을 붙여넣으라는 것
   - 페이지를 끝까지 본 뒤 OFF 하면 저장으로 선택한 것만 모아 질문을 뽑는다는 것
   - 주제 검색을 맡긴 모델(sonnet)과 그 근거

## 루프: 페이지 순회

사용자가 단락을 붙여넣을 때마다 아래를 수행한다.

### 0. 원본 페이지 검증

붙여넣은 단락이 지금 순회 중인 페이지 원문에 글자 그대로 있는지 `npm run --silent digest -- has <URL>`(단락을 heredoc stdin으로)로 대조한다.
Official Answer는 원문 그대로여야 하므로, X 문장이 있으면 해설하지 않고 X 문장과 `원문:` 줄을 보여 주며 다른 페이지의 단락인지 복사하며 글자가 섞인 것인지 묻고, 답에 맞게 고친 단락으로 진행한다.
새 URL을 받으면 이 단락부터 그 URL이 순회 중인 페이지다. 그 URL로도 ON의 준비(`page`)와 겹치는 것 알리기의 찾기를 한 뒤 다시 대조하고, 새로 찾은 파일은 겹침 목록에 추가하고 채팅에 알린다.

`원문에 없는 앞부분:` 줄이나 `(이 페이지에 비슷한 문장 없음)`으로 나온 부분이 주어·서술어 없는 나열형 문구(이미지 alt text·캡션)이면 묻지 않고 그 부분만 빼고 진행한다. 뺀 문구는 채팅에 알린다.

### 1. 문장마다 [인용 → 해설]: 브라우저 페이지로 띄운다

붙여넣은 단락의 **모든 문장·코드블록**을 문장 하나당 카드 한 장으로 만든다. 카드 칸은 넷이다.

1. **원문 인용**: 원문 그대로 옮긴다. 이 인용이 OFF에서 Official Answer의 원본이 된다.
2. **한글 의역**: 원문 의미를 한국어로 푼다. 의역만 봐서는 알 수 없는 근거가 있을 때만 의역 뒤 괄호에 한 문장으로 덧붙인다. 그런 근거는 아래뿐이다.
   - 기존 knowledge 파일과 겹치거나 거기에 붙일 재료 (`knowledge/<경로>.md`를 적는다)
   - MP `docs/`와 겹치는 내용 (그 경로를 적는다)
   - 이 페이지가 아니라 다른 페이지·다음 절이 설명할 범위
   - 앞서 저장 판정한 선행 개념에서 그대로 도출되는 내용
   - 실무에서 드물어 버림으로 둔 이유와 그 메커니즘 (아래 저장 판정의 **이론적 타당 ≠ 실무 빈도**)
3. **영단어 해설**: 그 안의 중요 영단어와 이 문장에서의 의미를 짚는다.
4. **라디오 3택**: 저장 / 해설 / 버림. 기본값은 아래 저장 판정 기준으로 찍는다.

#### 의역·영단어 해설 받기

2·3은 메인이 작성하지 않고 Gemini에 맡긴다. 단락을 문장·코드블록 하나씩 나눈 JSON 배열로 넘긴다. `<URL>`은 0단계에서 이 단락을 대조한 URL이다.

```bash
npm run --silent digest -- gloss <slug> <URL> <<'SENTENCES'
["문장1", "문장2"]
SENTENCES
```

`{ round, cards }`가 출력된다. 회차 번호와 카드의 `src`·`ko`·`words`를 그대로 스펙에 옮기고, 메인은 2의 괄호 근거를 `ko` 끝에 덧붙이고 4의 판정을 찍는다.

원문 검사에서 실패하면 stderr의 처방대로 고쳐 다시 실행한다. Gemini 호출이 실패하면 stderr를 사용자에게 보이고 멈춘다. 메인이 대신 작성하면 사용자는 Gemini가 사용되지 않은 것을 모른다.

#### 단락 요약

단락 전체의 핵심을 비유와 함께 3줄 이내로 정리해 스펙의 `summary`에 담는다.

#### 페이지 만들기·열기

```bash
set -o pipefail
npm run --silent build-page -- digest-cards <<'SPEC_JSON' \
  | node "$HOME/WebstormProjects/main/ai-contexts/plugins/ac/contexts/local-html-roundtrip.mjs" open ka-digest - --slug <slug>-<회차>
{ ...스펙... }
SPEC_JSON
```

스펙은 `{ slug, round, summary, cards: [{ src, ko, words: [{ word, meaning }], verdict }] }`이다. `verdict`는 라디오에 미리 찍어 둘 AI 판정(`save`·`explain`·`drop`)이다.

메인이 덧붙이는 괄호 근거와 `summary`는 HTML로 들어간다. 굵게·코드 표시는 `<strong>`·`<code>`로 적고, 글자로 보여야 할 `<`·`>`·`&`는 `&lt;`·`&gt;`·`&amp;`로 적는다.

#### 채팅에 남기는 것

페이지를 열면 채팅에는 문장 수·회차, 열린 HTML의 절대경로, 문장마다 선택한 뒤 제출·클립보드 복사를 누르고 복사된 JSON을 붙여넣으라는 안내만 남긴다.

### 1-1. 선택 받기

사용자가 붙여넣은 JSON이 선택 결과다. `npm run --silent digest -- select <slug>`에 heredoc stdin으로 넘기고, 출력된 한 줄을 채팅에 보고하고 다음 단락을 요청한다.

### 2. 저장 판정

판정은 카드 라디오의 기본값으로 찍는다. 아래 기준은 그 기본값에 적용하고, 최종 결정은 사용자가 화면에서 한다.

#### 세 판정의 목적지

세 판정은 강도가 아니라 **목적지**로 갈린다. 저장은 `knowledge/`의 Q&A 재료, 해설은 `explained/`의 해설 재료이고, 버림은 아무 데도 안 남는다.

**해설**이 맡는 것은 **그 자체로는 외울 게 없지만 남이 읽을 때 이해를 돕는 문장**이다.

- 앞 문장의 개념을 그대로 풀어 보이는 예시·비유
- 사용자 도메인 안에서 개념의 적용 범위를 넓혀 보여 주는 사례 (도메인 밖 사례는 버림. 아래 **사용자 역할 기준 필터링**)

**버림**으로 남기는 것은 문서 유지보수 배너·목차 링크·계보 귀속처럼 해설에 실어도 독자에게 아무 도움이 안 되는 문장이다.

#### 버림·해설 판정 기준

knowledge에 안 넣는 기준은 **"알 필요가 없는가"**다.

**사용자 역할 기준 필터링**: 사용자의 역할·배경이 명확하면 그 역할과 무관한 전문 분야 내용은 기본값을 버림으로 둔다.
- 비개발 도메인 적용 사례(의료·반도체·물류 등) → 개발자 사용자에게 버림

**상대편이 사용하는 API는 내 코드가 달라질 때만 저장한다**: 사용자의 역할이 한쪽(웹)인데 문서가 양쪽(웹·앱, 프론트·백엔드)을 함께 다루면, 상대편이 호출하는 이름 자체는 저장하지 않는다.
가르는 것은 **그것 때문에 내 쪽 코드가 달라지는가**다. 달라지면 저장하되 질문은 내 쪽 결과를 묻는 각도로 세우고, 안 달라지면 해설로 내린다.
- **그 API가 왜 생겼는지의 플랫폼 사정**은 버린다. 상대편 사정이라 내 코드를 안 가르고, 해설에 실어도 내 쪽 이해를 돕지 않는다.

**이론적 타당 ≠ 실무 빈도**: 1차 소스 근거가 있어도 사용자 역할의 하위 맥락에서 마주칠 빈도가 낮으면 기본값을 버림으로 둔다.

**기계적 후속은 해설로 찍는다**: 같은 페이지에서 이미 저장한 개념에서 기계적으로 유추되는 API 사용 세부(값을 어디서 꺼내는지, 옵션을 어느 인자에 얹는지)는 해설로 두어 OFF에서 선행 질문의 해설에 흡수한다. 가르는 질문은 "그 개념을 알면 외울 게 아니라 그때 찾아보면 되는가"다. 난이도가 아니라 선행 개념에서의 도출 가능성이다.

**계보는 버리고 효용·지침은 저장한다**: 개념의 기원·귀속, 몇 가지 형태로 분류되는지, 어느 책·논문에 실렸는지는 버린다. 그것으로 무엇이 좋아지는지, 무엇을 하라는지, 대가가 무엇인지는 저장한다. 가르는 것은 형식(나열이냐 산문이냐)이 아니라 그 문장이 독자를 판단·행동하게 만드는가다.

#### 중복 검사

위 기준을 먼저 적용하고, 저장 후보로 남은 문장에 이 검사를 적용한다. 단락마다 한 번, 문장이 아니라 단락 전체를 놓고 기존 Official Answer와 겹치는지 본다.

찾는 범위는 knowledge/와 MP의 `docs/` 디렉터리들(node_modules 제외)이다. 테스트·컨벤션·원칙은 MP에 있는 일이 많다. ON 겹침 목록의 파일을 먼저 대 보고, 목록에 없는 개념만 새로 찾는다.

- 기존 Official Answer와 **완전히 동일한 문장**이면 버림
- **같은 개념의 다른 표현**(더 쉬운 설명, 다른 관점, 보충)이면 저장
- MP `docs/`와 겹치면 판정은 그대로 두고 괄호 근거에 그 경로를 적는다

단, ON 겹침 목록의 파일과 겹치면 완전히 같은 문장이어도 저장으로 찍는다. 그 파일을 다시 작성할지는 OFF에서 정하므로, 여기서 버리면 다시 작성할 때 재료가 빠진다.
